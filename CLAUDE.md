# VEF Framework Go — Agent Guide

Read this file before touching code. It covers architecture, conventions, and workflow requirements.

This file is the shared, self-contained source of truth for repository-wide agent instructions. `TESTING.md` may provide fuller examples, but any rule that must be followed reliably should also be summarized here.

## Essential Commands

```bash
go test ./...                  # Run all tests (required before submitting)
go test -race ./...            # Race detection
golangci-lint run              # Lint (auto-fix: golangci-lint run --fix)
go run golang.org/x/tools/gopls/internal/analysis/modernize/cmd/modernize@latest -test ./...  # Modernize checks
go run ./cmd/vef-lint ./...    # Repo-specific analyzers (auto-fix: -fix)
```

## Local Setup & Git Hooks

- After cloning, run `task setup` (install [go-task](https://taskfile.dev) first). It installs `lefthook` and, when missing, `golangci-lint` — preferring Homebrew, else falling back to `go install` (lefthook) or the official pinned script / winget (golangci-lint) — then wires the git hooks. Each install task is `status:`-guarded, so a tool is installed only when absent. **Without Homebrew, `lefthook` is installed via `go install` into `$(go env GOPATH)/bin`, which must be on your `PATH` or the hooks won't be found.**
- Hooks are managed by **lefthook** (`lefthook.yml`): the `commit-msg` hook runs commitlint (`.commitlintrc.json`, Conventional Commits + single-line); the `pre-push` hook runs `golangci-lint`, then the modernize analyzer, then `vef-lint`.
- `Taskfile.yml` also exposes `task lint` and `task modernize` as shortcuts for those checks.

## Task Workflow

1. **Simple tasks**: directly implement, write tests, run verification.
2. **Complex tasks**: plan architecture first and get confirmation before wide refactors, public API changes, or architecture changes. If the user explicitly asks for parallel agent work, split the work into independent scopes with clear file ownership.
3. **Code review**: after implementation, review code to ensure it hasn't drifted from the task goal.
4. **Tests**: all general tasks must include corresponding test code. `TESTING.md` has fuller examples, but the critical rules are summarized in this file.
5. **Simplification**: after each task, do a simplification pass yourself. Prefer smaller, clearer code over extra abstractions.
6. **Verification**: run the narrowest relevant checks during development, and finish with `go test ./...`, `golangci-lint run`, `go run golang.org/x/tools/gopls/internal/analysis/modernize/cmd/modernize@latest -test ./...`, and `go run ./cmd/vef-lint ./...` when the task scope allows it. All required checks green = feature complete.

## Definition of Done

- The requested behavior or analysis is complete and scoped correctly.
- Relevant tests or documentation are added or updated when needed.
- Verification was run and the result was reported.
- `AGENTS.md` is a pointer to this file — never duplicate guide content there; all conventions live here only.

## Architecture Overview

- **Stack**: Go 1.27.0 + Fiber v3 + Uber FX + Bun ORM. The 1.27 floor buys **generic methods**, and their one restriction shapes the API: a type parameter is legal on a method of a concrete or generic *type* (`page.Page[T].Map[R]`) but **never in an interface** — `interface method must have no type parameters`, a permanent restriction rather than an omission, since an interface's method set would otherwise be unbounded. So the typed entry points that take one of the framework's ~190 exported interfaces stay package-level functions and cannot be folded into their receiver: `event.SubscribeTyped[T](bus, …)`, `integration.Call[T](ctx, inv, …)`, `cqrs.Send[A, R](ctx, bus, a)`, `expression.EvaluateAs[T](ctx, engine, …)`. The other 1.27 language change, **promoted fields in struct literals**, is adopted repo-wide: a literal sets an embedded type's fields directly (`storage.FileRecord{ID: …, CreatedAt: …}`, not `{CreationAuditedModel: orm.CreationAuditedModel{…}}`), which is what modernize's `embedlit` enforces — so a new model or payload literal must be written that way or the pre-push hook fails. Default language: Simplified Chinese (`VEF_I18N_LANGUAGE`). **Builds with `CGO_ENABLED=0`** — the built-in expression engine (`expression.Module`, in the core boot list) uses the pure-Go `expr-lang` (`github.com/expr-lang/expr`), so no cgo toolchain is required.
- **Structure**: public packages at root (`api`, `crud`, `orm`, `datasource`, `security`, `result`, etc.), internal implementations under `internal/`.
- **Boot sequence** (`vef.Run()` in `bootstrap.go`): `config → datasource → middleware → api → security → event → expression → js → cqrs → cron → redis → lock → mold → storage → sequence → event tx_memory → event outbox → event redis stream → event inbox → schema → monitor → mcp → push → app → [host options] → cron start`. `Run` delegates to `bootOptions`, which hands its environment prefix and the host's options to `bootmodules.Assemble` — the single authority for boot order: prefix → core modules → host options → the trailing `fx.Invoke` slot that starts the cron scheduler (see the scheduler gotcha) — then appends `startApp`. `internal/apptest` composes through the same function rather than repeating the order, so the two graphs cannot drift and one test covers both. The `datasource` step is a single FX module — `datasource.Module` builds the registry, seeds static/provider sources, exposes the primary `*sql.DB`, and derives the primary `orm.DB` from the Registry. **Layering is `datasource → orm → database`, with `orm` and `database` mutually unaware**: `internal/database` connects a `config.DataSourceConfig` into a `*sql.DB` (no bun ORM imports beyond the SQL drivers, no FX module); `internal/orm` takes an already-connected `*sql.DB` and wraps it into `orm.DB` via `orm.Open(sqlDB, kind, opts...)` (it owns all bun assembly — dialect via `orm.DialectFor`, query hook, `internal/orm/sqlguard` — and never imports `database`); `internal/datasource` is the only composition root that knows both, calling `database.Open` then `orm.Open`. The registry stores `orm.DB` + the `*sql.DB` lifecycle handle; the `*bun.DB` lives only inside the `orm.DB` wrapper. The public **`datasource`** package defines the contract (`Registry`, `Provider`, `Spec`, options, errors); `internal/datasource` implements it (internal → public, like `storage`). The `*bun.DB` wrapper and connection internals are never re-exported through the public `orm` package; `orm/bun.go` does deliberately re-export a curated set of bun model/query types and hook interfaces for model authoring.
- **Modules**: each exposes `fx.Module` in `internal/<module>/module.go`, constructors annotated into FX groups.
- **DI helpers** (`di.go`): `vef.ProvideAPIResource(...)`, `vef.ProvideMiddleware(...)`, `vef.ProvideAuthStrategy(...)`, `vef.ProvideAuthenticator(...)`, `vef.ProvideSPAConfig(...)`, `vef.SupplySPAConfigs(...)`, `vef.ProvideCQRSBehavior(...)`, `vef.ProvideMCPTools(...)`, `vef.ProvideDataSourceProvider(...)`, `vef.ProvideJSLib(...)`, `vef.ProvideIntegrationOutboundAuthScheme(...)`, `vef.ProvideIntegrationInboundAuthScheme(...)`, `vef.ProvideIntegrationInboundHandler(...)`, `vef.ProvideCronJobHandler(...)`, `vef.ProvideSessionRevocationListener(...)`, `vef.ProvideApprovalGlobalsResolver(...)`, `vef.ProvideApprovalAssigneeResolver(...)`, `vef.ProvideApprovalCCResolver(...)`, `vef.ProvideApprovalInitiatorResolver(...)`, etc. (`approval.Service` — the programmatic flow-control surface — is *injected*, not provided; see the approval gotcha.) The shared, ordered business-module list lives in `internal/bootmodules` and is reachable only through `bootmodules.Assemble` — both `vef.Run` and the `internal/apptest` harness compose through it, so neither the module list nor the boot order can drift.
- **Optional feature modules**: not in the default boot; enable by passing to `vef.Run(...)`. `vef.ApprovalModule` turns on the approval/workflow feature (its `approval.*` events need a transactional route — see the approval gotcha). `vef.IntegrationModule` turns on the integration engine — config- and script-driven adapters translating between external systems and the app's standard contracts (see the integration gotcha).

## API Patterns

- **Resources**: `api.NewRPCResource(name, api.WithOperations(...))` or `api.NewRESTResource(name, opts...)` with optional CRUD generics (`crud.FindAll[M,S]`, `crud.Create[M,P]`, etc.).
- **Registration**: `vef.ProvideAPIResource(constructor)`.
- **Handlers**: PascalCase auto-resolution (`Action: "create_user"` → `CreateUser`), or explicit `Handler` in `api.OperationSpec`.
- **Parameter binding**: sentinel types `api.P` (params) and `api.M` (meta), `search` tags for queries (`search:"eq"`, `search:"contains,column=name|description"`). **Params decoding is permissive but never silent**: a request key the target struct declares no field for is ignored — so a client still sending a retired field keeps working — and reported. `Params.DecodeReportingUnmapped` returns those keys (nested ones by path, e.g. `trigger.at`) and the params resolver logs them once per operation × key set, bounded because the key carries caller-supplied names. There is no strict/reject mode: a closed contract is expressed by the report, not by a 400. Framework-level query parameters (`security.QueryKeyAccessToken`) are stripped by the REST router and never enter the business parameter space — authentication reads them off the fiber context — so anything reported really is drift. Built-in resolvers: `fiber.Ctx`, `orm.DB`, `log.Logger`, `*security.Principal`, `mold.Transformer`. Custom: `group:"vef:api:handler_param_resolvers"`.
- **Response**: `result.Ok(data)`, `result.Err("msg", result.WithCode(code))`.

## Request Lifecycle (`/api`)

Request parsing → Authentication (JWT/signature/IP/password) → Context enrichment (DB, logger, principal) → Authorization (`RequiredPermission`) → Rate limiting (default `vef.api.rate_limit`: 100 req/5min, keyed per operation × client, counted per node; per-endpoint override via `OperationSpec.RateLimit`) → Handler dispatch (30s timeout).
RPC uses `POST /api`; REST routes are mounted under `/api/<resource>`.

## Data Access

- `orm.DB` for queries against the **primary** data source and `db.NewRaw(...)` for raw SQL when needed.
- Multi-source: inject `datasource.Registry` and call `sources.Get("<name>")` (or `Primary()`). `Get` returns `orm.DB`. The registry covers `Register`, `Update`, `Unregister`, `Reconcile`, `TestConnection`, `HealthCheck`, `Has`, `Names`, `Kind`. `TestConnection(ctx, cfg)` opens a throwaway connection, proves it by querying the server version, then closes it — returning `datasource.ConnectionInfo{Version}` without ever touching the registry (the entry point behind a UI "test connection" button). Static sources come from `vef.data_sources.<name>` in TOML; runtime sources come from a `datasource.Provider` (`vef.ProvideDataSourceProvider(...)`) or direct `Register`. For periodic sync against an external table, schedule a cron job that calls `sources.Reconcile(...)`.
- Models embed `bun.BaseModel` (table tag) + `orm.FullAuditedModel` (id + audit: `created_at/by`, `updated_at/by`). Variants: `orm.Model` (id only), `orm.CreationTrackedModel` (creation audit, no id), `orm.FullTrackedModel` (full audit, no id), `orm.CreationAuditedModel` (id + creation audit). IDs: `id.Generate()` → 20-char XID.
- **SQL log noise control**: `orm.WithQuietSQLLog(ctx)` demotes that context's successful statement logs from Info to Debug. Every built-in polling loop marks itself this way — the durable cron engine (claim/sweep/heartbeat/journal), the approval timeout/pre-warning/cleanup scanners and the business projection worker, the storage claim sweeper and delete worker, the event outbox relay and outbox/inbox cleaners, and the integration log pruner — and the in-memory scheduler's gocron job monitor logs routine scheduled/completed events at Debug for the same reason. Mark host polling loops the same way. Slow-query warnings and failures always keep their level, and handler/business contexts stay unmarked so business queries log normally. **The mark must never survive the handoff to host code**: `orm.WithoutQuietSQLLog(ctx)` lifts it again, and the framework applies it where a marked loop reaches host-owned surface — the approval timeout scanner processes each timed-out task under a lifted context (host lifecycle hooks, assignee/user resolvers, real business writes), and the eventual business-projection worker lifts it for the write against the host's business row so the eventual lane logs that statement exactly like the synchronous lane does from a request handler. Only the loops' own bookkeeping stays demoted. Static dialect facts are not statement logs and are not routed through the mark: a locking clause dropped because the dialect cannot honor it (SQLite row locks, PostgreSQL-only modes on MySQL) warns once per process per dialect/mode, not once per query.
- Transactions: `db.RunInTx(ctx, func(txCtx context.Context, tx orm.DB) error { ... })`. Cross-source transactions are **not supported**; an event published with `event.WithTx(tx)` requires a tx opened from the primary source. `orm.OnCommit(txCtx, fn)` registers work that must happen iff the surrounding unit of work became durable: hooks fire after the **outermost** commit in registration order, registrations inside a nested `RunInTx` are discarded when that savepoint rolls back (bun implements nesting as a savepoint), the callback gets a cancellation-detached context so a disconnected client cannot suppress work whose transaction already committed, and it cannot report failure — there is nothing left to roll back. Outside an **open** `RunInTx`/`RunInReadOnlyTx` scope it returns `orm.ErrNoCommitScope` rather than silently running immediately or accepting a registration that can never fire — that covers manual `BeginTx` transactions (no context to carry the collector) and a context captured by a goroutine whose transaction has already committed.
- Search: `search.Applier[T]` with struct tags.

## Security

- `security.Module`: JWT, password, OpenAPI authenticators + `AuthManager` aggregator.
- `security.Principal`: `Type`, `Id`, `Name`, `Roles`, `Details`. Config in `vef.security`.
- RBAC via `NewRBACPermissionChecker` + user-provided `RolePermissionsLoader`.
- **Login password hardening** (public `security` package, wired in `security.Module`, all opt-in):
  - **Encrypted transport**: register a `security.PasswordDecryptor` (e.g. backed by `cryptox.NewRSA`) and the `PasswordAuthenticator` decrypts the transmitted credential to plaintext before verifying it against the stored hash. Decryption lives at the authenticator layer, so the `password.Encoder` stays a plain KDF for both storage and comparison (there is no `cipherEncoder`).
  - **Brute-force lockout**: `security.LoginGuard` (default `MemoryLoginGuard`; swap `NewRedisLoginGuard` via `fx.Decorate` for multi-node) throttles the login endpoint before authentication, keyed per `vef.security.lockout.key` (`user` / `ip` / `user_ip`, default `user_ip`). On by default (`max_failures` 10); `strategy` is `lock` (hard block) or `backoff` (escalating delay). A trip returns `security.ErrAccountLocked` (HTTP 429); guard-store errors fail open. Integrated in `AuthResource.Login` **and** `ResolveChallenge` — failed second-factor guesses count toward the same lockout key, and a tripped lockout blocks both endpoints.
  - **Password strength**: `security.PasswordValidator` (config-backed `NewRuleBasedValidator` over `vef.security.password_policy`, composable `PasswordRule`s: length, character classes, disallow-identity, blocklist) runs inside `PasswordChangeChallengeProvider` before persisting; inject it into custom registration/reset flows too. Violations are `ErrCodePasswordPolicyViolation` (HTTP 400).
  - **Password history (reuse prevention)**: app implements `security.PasswordHistoryStore` (`Recent` for the check, `Add` called from its own `ChangePassword` — the framework reads and compares, the app writes). When registered with `password_policy.history_depth > 0` the module composes a `NewHistoryValidator` into the validator via `NewChainValidator`; reuse is `ErrPasswordReused`.
  - **Password expiry**: app implements `security.PasswordMetadataLoader`; `NewExpiryPasswordChangeChecker(loader, maxAge)` emits the `expired` forced-change challenge. Compose multiple reasons with `NewCompositePasswordChangeChecker(...)`.
- **Login challenge payloads are host-shaped, and the framework only transports them**: a `ChallengeProvider` puts anything on `LoginChallenge.Data`, and the React starter types challenges through host `Register['challenges']` augmentation rather than shipping a renderer per type (only `password_change` has a built-in one). So both ends of a challenge payload are host code, and the framework's job is to carry it intact. Both built-in data structs therefore expose `Meta map[string]any`, filled by the host's own hook — `PasswordChangeChecker.Check` and `DepartmentLoader.LoadDepartments` each return the whole `*...ChallengeData`, never just the parts the framework understands. For department selection that means **`ID` is the only field the framework is party to** (`Resolve` hands it to `DepartmentSelector` untouched); `Name` and the per-option `Meta` — owning organization, `parentId` for tree rendering, ancestry path — are display data it never reads. Deliberately untyped: organization-to-department modelling is host domain knowledge (depth, matrix orgs), and nothing in the framework or the starter would consume a typed `ParentID`. Type it only if the starter ever ships a generic department renderer, which is an additive change since `Meta` stays. Put an org hierarchy in the **challenge-level** `Meta`, not as extra `Departments` entries: `Evaluate` reads a non-empty list as "ask the user" and `Resolve` forwards any listed ID to `DepartmentSelector`, so a grouping node listed as an option becomes selectable.
- **Login token mechanisms** (`vef.security.token_type`, default `jwt_token`): the two are independent — session control is only available with `opaque_token`.
  - **`jwt_token`** (`AuthTypeJWTToken`): stateless, self-contained access+refresh JWTs; zero server lookup, unrevocable before `exp`.
  - **`opaque_token`** (`AuthTypeOpaqueToken`): a random reference token backed by a server-side `security.SessionStore` (default `MemorySessionStore`, built on the in-memory TTL cache so expired sessions are GC'd instead of accumulating; swap `NewRedisSessionStore` via `fx.Decorate` for multi-node). `OpaqueTokenAuthenticator` looks the token up per request (Principal snapshot from the session) and slides its idle TTL up to the absolute `Session.ExpiresAt` (the max-lifetime cap, authoritative in both stores and clamped at issue time too, so `idle_ttl > max_lifetime` cannot outlive the cap); `OpaqueTokenGenerator` opens the session and enforces `vef.security.session.max_concurrent` via `on_exceed` = `reject` or `evict_oldest` (default: new login kicks the earliest device — 挤下线). The concurrency cap is **best-effort under concurrent logins** (count-then-create may briefly overshoot). Sessions are keyed by `HashOpaqueToken` (never the raw token). `AuthResource.Logout` revokes the current session (a no-op for JWT); over-limit login returns `security.ErrTooManyConcurrentSessions` (HTTP 403). Both the bearer path (`AccessTokenAuthenticator`) and MCP dispatch the configured token type; `TokenGenerator.Generate(ctx, principal, SessionMeta)` is mechanism-agnostic.
  - **Only the configured mechanism's authenticators are registered** (`newTokenAuthenticators`, flattened into the authenticator group): under `opaque_token` a leftover JWT (access or refresh) no longer authenticates anywhere, and the `refresh` operation is not mounted at all (sessions self-renew). `Login` also refuses the framework-issued token types (`jwt_token` / `opaque_token` / `refresh`) as login credentials, so a stolen short-lived access token cannot be laundered into a long-lived refresh token or extra session.
  - The `SessionStore` is exposed in DI (not private) so apps build their own session-admin endpoints (with their own authorization) via `ListByUser` / `Revoke` / `RevokeUser`; a cross-user "all online sessions" view uses the optional `security.SessionInspector` (`ListAll`, type-asserted, mirroring `event.StreamInspector`) implemented by both built-in stores — the Redis one via keyspace `SCAN` (no global index set to accumulate). The Redis store makes every multi-key mutation atomic (MULTI/EXEC) and guards sliding renewal with `SET … XX` so it cannot resurrect a concurrently-revoked session; the per-user id set carries a TTL refreshed on create/renew (renewal also re-`SAdd`s membership to self-heal), and `RevokeUser` removes only the enumerated ids so a racing login is never left invisible to `ListByUser`.
- **Trust login (类单点登录)** (`vef.security.trust_login`, off by default): a third-party system links a user straight into the app with a signed handoff. Two legs, both required. The **gateway** is an `app.Middleware` real route (`GET /sso/trust`, order 460) that verifies an HMAC over `app_id + method + path + user_id + redirect + timestamp + nonce`, resolves the external user, parks the identity under a one-time `security.TrustCodeStore` code (default TTL 60s, keyed by `HashOpaqueToken`), and 302s to `<redirect>?app_id=…&code=…`. The **exchange** is `security.TrustCodeAuthenticator` (`type: "trust_code"`, `principal` = app ID, `credentials` = the code) plugged into the ordinary `security/auth.login` pipeline, so a handoff inherits the **full challenge chain**, token issuance, session concurrency and the login audit event unchanged. The one thing it does *not* inherit is the brute-force guard (`unguessableAuthTypes` in `auth_resource.go`): a code is `GenerateOpaqueToken` randomness, single-use and seconds-lived, so no number of attempts approaches it, while the identity it presents is the initiating system's app ID rather than a person — counting failures would put every user of that system in one lockout bucket that anyone able to POST a wrong code could fill (`TestBogusCodesDoNotLockOutTheApp`). Its throttles are the gateway rate limit below, the code's single use, and `vef.security.login_rate_limit`. The exemption lives in `Login`, not in the guard helpers, because those are shared with `ResolveChallenge` where the type in hand is a challenge type and a challenge answer very much is guessable. Deliberately **no "skip challenges" switch**: department selection is a required business input, and a forced `password_change` is policy — skipping either would be a hole, and skipping a second factor is a per-provider decision, not a blanket one. Signing secrets come from `security.ExternalAppLoader` (the same source API signature auth reads, so no secret enters a config file) while **`vef.security.trust_login.apps.<appId>.redirect_urls` is a separate grant**: being able to call the API never implies being able to log a user in, and an app absent from that map is refused. A redirect must match an entry's scheme+host exactly and sit under its path (segment-wise, dot segments resolved). `security.TrustUserResolver` is optional — with none registered the gateway resolves through `UserLoader.LoadByID`, already correct when both systems key users by the same identifier — but **whichever of the two runs is making an authentication decision**: the external system vouched for who the user is, not for whether this application still admits them, so it must refuse a disabled/locked/expired account the way the password path does. Hosts commonly keep that check in `LoadByUsername` alone, where trust login never reaches it. Codes are bound to the redirected browser's User-Agent by default (`bind_user_agent`, `bind_client_ip` off since mobile networks change). The code store is **topology-selected like `lock.Locker`**, not memory-unless-decorated: Redis when the client is available (GETDEL, so Redis 6.2+), otherwise in-memory with a boot warning — a memory store cannot serve a second replica at all, since a code issued on one node is unknown to every other and the exchange fails outright rather than merely weakening. The shared `security.NonceStore` is selected the same way and for the same reason (memory would make one signed handoff URL navigable once per replica); its boot warning is raised only while trust login is on, since a per-process nonce store merely weakens a server-to-server API call but hands a browser-visible credential a fresh redemption per node. The gateway is rate-limited per (app ID, client IP) via `vef.security.trust_login.rate_limit` (default 120/min, per node) — it is public and does an `ExternalAppLoader` lookup before it can reject anything — and its 302 carries `Cache-Control: no-store` plus `Referrer-Policy: no-referrer` so neither the code in `Location` nor the signature in the request URL travels further than it must. Two sharp edges worth stating to whoever implements the signing side: the signed `path` must match exactly, and `StrictRouting` is off, so `/sso/trust/` reaches the gateway but hashes differently and yields a permanent opaque 401. Gateway failures render as plain text with the error's status, never a JSON envelope, since the endpoint is navigated to directly; every verification failure collapses into `security.ErrTrustAuthFailed` so app IDs cannot be enumerated.
- **API auth strategies** (`internal/api/auth`): built-in `none` / `bearer` / `signature` / `ip` / `api_key` / `http_basic`, selected per resource via `api.WithAuth` (`api.Public()`, `api.BearerAuth()`, `api.SignatureAuth()`, `api.IPAuth(name)` — the no-arg `api.IPAuth()` targets the `default` whitelist —, `api.APIKeyAuth(header)` — no-arg reads `X-API-Key` —, `api.HTTPBasicAuth()`); custom strategies register with `vef.ProvideAuthStrategy(...)`. The `ip` strategy treats the client IP as the credential: it resolves the named whitelist through `security.IPWhitelistLoader` — default is the config-backed loader over `vef.security.ip_whitelists` (map of name → IP/CIDR entries, validated fail-fast at boot; TOML keys are lowercased); registering a custom loader (DB / config center) replaces it entirely. All failures deny with `security.ErrIPNotAllowed` (fail closed; an empty whitelist denies, never allows). Behind a reverse proxy `vef.app.trusted_proxies` must be configured or the whitelist sees the proxy address. `api_key` / `http_basic` follow the same loader pattern: verification cores live in `security` (`APIKeyLoader.LoadByKey` — comparison inside the implementation, constant-time when scanning; `BasicAccountLoader.LoadByUsername` — returns the stored secret, the framework compares constant-time), defaults are config-backed over `vef.security.api_keys` / `vef.security.basic_accounts` (name → key/roles, username → password/roles; validated fail-fast at boot), failures deny uniformly with `security.ErrAPIKeyInvalid` / `ErrBasicCredentialsInvalid` (401, no username-vs-password leak), and matched principals are synthesized external apps (`api_key:<name>` / `http_basic:<username>`) carrying the configured roles.

## Configuration

- `application.toml` from `./configs`, `./`, or `VEF_CONFIG_PATH`. Sections: `vef.app`, `vef.api` (default operation rate limit: `rate_limit.max` / `rate_limit.period`), `vef.data_sources.<name>` (primary mandatory), `vef.cors`, `vef.security` (trust-login SSO under `vef.security.trust_login`), `vef.redis`, `vef.cache`, `vef.storage`, `vef.integration`, `vef.cron` (durable schedule store under `vef.cron.store`), `vef.push`, `vef.approval` (optional module; `form_data_max_bytes` bounds the submitted form payload).
- `config.Config.Unmarshal` with `config:""` struct tags. Env overrides: `VEF_CONFIG_PATH`, `VEF_LOG_LEVEL`, `VEF_I18N_LANGUAGE`.
- **Defaulting convention**: prefer immutable `Effective*()` accessors on the config struct (e.g. `StorageConfig.EffectiveClaimTTL`, `EventConfig` accessors) over mutating the parsed value — the default lives next to the field, the parsed config is never silently rewritten, and consumers opt in at the read site. Treat the parsed struct as raw input that may hold zero values; do not assume a field is populated. (`ApprovalConfig.ApplyDefaults`, called once in `internal/config`, predates this rule and is the lone mutate-at-load exception.)

## Middleware Stack (by `Order()`)

Compression (`-1000`) → Headers (`-900`) → CORS (`-800`) → Body-Encoding (`-750`, decodes an opt-in `X-Body-Encoding` request body back to raw JSON before the guard/parse, scoped to `/api`) → Content-Type (`-700`, JSON/multipart guard scoped to the `/api` surface only — MCP, the storage proxy, and the integration inbound gateway own their body formats) → Request ID (`-650`) → Logger (`-600`) → Recovery (`-500`) → Recorder (`-100`) → [routes] → integration inbound / push / trust-login gateway (`+460`) / MCP / storage proxy (positive orders) → SPA (`+1000`). Custom: `vef.ProvideMiddleware(...)`, whose constructor must return the public `app.Middleware` (see the host-contract gotcha).

## Development Conventions

- **Commits**: [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Single logical change per commit, message **strictly one line** — enforced by commitlint via the `commit-msg` hook (`body`/`footer` must be empty), so flag breaking changes with the header `!` form (`feat!:`, `fix(scope)!:`) instead of a `BREAKING CHANGE:` footer. No co-author trailers. Split by feature granularity. Types: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`. Scopes optional: `refactor(test):`, `feat(crud):`.
- **Releasing**: update `version/version.go` (`VEFVersion` constant) → commit with `chore: bump version to vX.Y.Z` → `git tag vX.Y.Z` on that commit → push. The tag must always point at the version-bump commit, not an earlier one.
- **Code style**: lean handlers (delegate to services), composable FX modules, `fx.Annotate` with precise tags.
- **Identifier naming**: when a name contains consecutive acronyms, keep the semantically more important acronym in standard form and Pascal-case the other for readability. Prefer `HTTPSUrl`, `HttpsURL`, `JSONApi`, or `JsonAPI`; avoid fully stacked forms like `HTTPSURL` or `JSONAPI`.
- **Time field naming**: a time value's representation must be readable off its name. Structured instants (`timex.DateTime` / `time.Time`) take a bare `<verb>At` — `createdAt`, `finishedAt`, `expiresAt` — because the type already carries epoch and precision. Numeric instants spell out both (`<name>AtUnixMs`); numeric durations spell out the unit (`<name>Ms`, `<name>Seconds`, `<name>Hours`), milliseconds abbreviating to `Ms` and coarser units spelled out. Window bounds are verb-form `startsAt` / `endsAt`, never `startTime` / `endTime`. The suffix is load-bearing rather than decoration: `cron.TriggerSpec` carries `EveryMs int64` beside `At *time.Time`, and `ScheduleSpec.Timeout` (`time.Duration`, nanoseconds) sits one conversion away from `Schedule.TimeoutMs` (`int64`, milliseconds) — drop the suffix and those become same-named fields whose values differ by 10⁶, with the conversion no longer visible at the assignment. Keep one unit word per module: cron says `Ms` everywhere (`unixMsPtr`, `ceilUnixMs`), never `Milli`/`Millis`.
- **Unused parameters & receivers**: omit the name entirely for unused receivers (`func (*Type) Method(...)`) and for parameter lists where every entry is unused (`func F(context.Context, string) error`). Do **not** write `_` in those cases. Only fall back to `_` when at least one parameter in the list is used — Go syntax requires every entry in a list to be either all-named or all-unnamed, so a partially-unused list must keep `_` for the unused entries (e.g. `func (s *Svc) Get(_ context.Context, key string) (...)`). **This convention is machine-enforced** by `vef-lint`'s `unusedrecv` and `unusedparam` analyzers, both of which carry an automatic fix (`go run ./cmd/vef-lint -fix ./...`); no golangci-lint linter can express it, because revive's `unused-receiver` / `unused-parameter` accept `_` as the answer and have no notion of "the whole list is unused".
- **Empty struct methods**: use pointer receivers (`func (*T) Method(...)`) even for zero-size structs, for consistency with the rest of the codebase.
- **Empty struct pointer initialization**: use `new(T)` instead of `&T{}` when constructing a pointer to a zero-value struct.
- **No compile-time interface assertion vars**: do not write `var _ Iface = (*impl)(nil)` witness declarations. Interface conformance is proven by constructor return types and by tests that exercise the type through the interface.
- **Comments**: only for exported types, complex logic, and non-obvious details. Explain "what" and "why", not "how". Do not add package-level comments such as `// Package foo ...`; keep package documentation out of source files unless explicitly requested. **Interface methods must always have comments** — interfaces are extension points for framework users.
- **Test style**: use `testify/suite` only when lifecycle hooks or shared state are required; prefer simple table-driven tests for pure functions.
- **Test file layout**: tests for `foo.go` belong in `foo_test.go`. If tests span multiple source files, split them by source file. Put test helpers immediately after imports.
- **Test quality**: cover behavior, not just line coverage. Include boundary cases such as zero/default values, whitespace inputs, nil vs empty, option override precedence, and argument passthrough correctness when relevant.
- **Assertions**: suite tests must use instance methods such as `s.Require()` and `s.Equal()`. Non-suite tests use standalone `require` and `assert`. Every assertion needs a descriptive message.
- **Test naming**: never use underscores to encode sub-scenarios in test method names (`TestFoo_Bar`). Use nested subtests: `s.Run("Bar", func() { ... })` inside a single `TestFoo` method, producing clean hierarchies like `TestSuite/TestFoo/Bar`.
- **Interface placement**: interfaces live next to their most relevant code, never in a centralized `interfaces.go`. Place each interface in the file that defines its feature context (e.g., `PasswordChangeChecker` in `password_change.go`). When 3+ related interfaces form a sub-domain cluster, create a dedicated file (e.g., `permission.go`). Same rule applies to types — no centralized `types.go`.
- **Collections & Streams**: prefer `github.com/coldsmirk/go-collections` and `github.com/coldsmirk/go-streams` when they improve clarity. For validation or lookup sets, use `collections.NewHashSetFrom(...)` + `.Contains()` instead of `map[T]struct{}`. Keep a plain `for` loop when it is already the clearest option; streams are best for multi-step transforms, nested iteration, or error propagation.
- **Integration tests**: use `internal/apptest.NewTestApp` for app-level integration testing. For multi-database tests, only skip cases that are fundamentally impossible to simulate.

## Error / i18n Convention

A single convention governs every module that surfaces API errors. New modules MUST follow it; deviations are bugs.

- **Two-file split per module**:
  - `<module>/errors.go` — internal `errors.New` sentinels (configuration faults, type assertions, reflective failures) consumed only within the module.
  - `<module>/api_errors.go` — outward-facing `result.Error` sentinels with i18n message, status code, and business code. Public API surface.
  - Modules with no internal sentinels skip `errors.go`; modules with no outward errors skip `api_errors.go`.
- **i18n key namespace**: every key carries its module prefix — `approval_*`, `monitor_*`, `storage_*`, `schema_*`, `api_*`, `security_*`. Cross-cutting keys in `result` package (`ok`, `error`, `record_not_found`, etc.) are unprefixed and reserved for that package.
- **Constant naming**:
  - `ErrCode<Name>` — int business code (e.g. `security.ErrCodeTokenInvalid`).
  - `ErrMessage<Name>` — i18n key string. **Only define when the key is referenced cross-file**: dynamic templates (callers pass template params via `i18n.T(key, params)`), factory-style errors (`ErrCredentialsInvalid(msg)`), or Fiber/external mapping tables. For purely sentinel-internal keys, inline the string literal at the sentinel definition (`i18n.T("security_signature_invalid")`) — do not introduce a named constant.
  - `Err<Name>` — `result.Error` sentinel (e.g. `security.ErrTokenInvalid`).
- **Sentinel vs inline**: prefer a sentinel when ≥2 callers return the same error; inline at the call site only when an error is genuinely single-use and parameterised.
- **`errors.Is` semantics**: `result.Error.Is` compares `Code` alone, so dynamic factories (`Errf`, `ErrNotImplemented`, `security.ErrCredentialsInvalid`) match their corresponding sentinels. Do not rely on message-string equality for identity.
- **Dependency direction**: business modules import `result`; `result` MUST NOT import any business module. New error codes / messages live next to the code that raises them, never in `result`.

## Gotchas

- `db.RunInTx` — use `Tx` casing, not uppercase `TX`.
- **Data sources**: `vef.data_sources.<name>`, primary mandatory (no legacy `vef.data_source` fallback — there is no backward compatibility). Internal modules (approval, storage, event inbox/outbox, schema reflection, CRUD) all operate on the **primary** source only — additional sources are application-level concerns. Cross-source transactions are not supported; `event.WithTx(tx)` must use a tx opened from the primary. `datasource.Registry.Unregister` removes the entry atomically and closes the underlying connection asynchronously (honoring `WithCloseGrace`): callers that already hold an `orm.DB` reference can drain in-flight queries, while the next `Get` returns `datasource.ErrNotFound`. `WithCloseGrace` applies to `Update`/`Unregister` only — `Register` never closes a connection and takes no options. `Reconcile` serialises concurrent reconciles (registry-wide mutex) so two ticks of a refresher job never interleave; direct `Register`/`Update`/`Unregister` are not synchronised with a running `Reconcile`.
- `SupplySPAConfigs` — all caps SPA, not `SupplySpaConfigs`.
- `api.OperationSpec` — not `api.Spec`.
- CRUD embedding uses interface names as field names: `crud.FindAll[M,S]` not `*crud.FindAllApi`. Constructor: `crud.NewFindAll[M,S]()`.
- Boot sequence includes `sequence`, event transport submodules, `schema`, and `mcp` modules — often missed when listing module order.
- **JS scripting is capability-based, two tiers** (`js/` + `internal/js`): the DI `*js.Engine` installs an always-on baseline into every runtime — the pure-JS stdlib bundle (one lib named `stdlib` exposing each library under its ecosystem-native global: BigNumber / dayjs / fxp (fast-xml-parser) / radashi / z (zod), plus the core-js URL / URLSearchParams polyfills; zod ships the en + zh-CN locales with zh-CN issue messages as the default, and the single vendored file `js/libs/stdlib.bundle.js` is rebuilt via `task js:stdlib` from the pinned esbuild project in `js/libs/build` — bump a version in its `package.json`, rebuild, done) plus three framework **utility** libs `internal/js` seeds via `js.WithBaseLibs`: `console` (info/warn/error onto `logx.Logger.Named("js")`), `crypto` (hashx digests/hmac + base64/hex/uuid), `cache` (in-memory `cache.Cache[any]`, `js:`-prefixed keys). The three side-effecting **capability** libs are seeded into the **catalog** (`js.WithLibs`) at safe defaults and stay **opt-in per runtime**: `events` (publish-only), `http` (30s timeout, otherwise unrestricted), `sql` (read-only over primary `orm.DB`) install only when `Engine.NewRuntime` is called with `js.EnableLibs("http", ...)` (plus `js.WithRunTimeout` / `js.WithMaxCallStackSize`) — this gate is what lets one engine serve both low-trust and high-trust scripts. **Override by name, tier-preserving**: `vef.ProvideJSLib(...)` (group `vef:js:libs`) returning a lib whose `Name()` matches a built-in replaces that default keeping its tier (override `cache` → still always-on; override `sql`/`http` → still opt-in) with the app's own policy (enable `sql.execute`, restrict HTTP with `WithPublicNetworkOnly` / `WithAllowedHosts` / `WithMaxBodySize`, back the cache with Redis, restrict events with `WithAllowedTypes`); a fresh name joins the opt-in catalog. A `js.Runtime` is single-goroutine and per-execution; host libs must issue IO through `Runtime.Context()`. `jshttp` is a synchronous fetch-aligned API (`http.fetch` + verb sugar; response carries `status/statusText/ok/url/redirected/headers/body/text()/json()/arrayBuffer()`; redirect modes follow/error/manual). `sql.queryList` is enforced read-only fail-closed through `sqlguard.EnsureReadOnly` (AST-based; writing CTEs, stacked statements, dialect side-effecting functions, and unparseable SQL are rejected — `?` placeholders are literal-substituted before parsing). Per-execution data (principal, form data) is bound via `Runtime.Set`, never modeled as a lib. goja offers no per-runtime memory limit — bound scripts with the run timeout, stack size, and the libs' opt-in caps. **Default posture caveat**: the built-in `http` reaches any address (no SSRF guard) and `sql` reads the whole primary DB; both are inert until `EnableLibs`, but a call site that enables them for an untrusted script should override with a tightened lib first.
- **`httpx` is the outbound HTTP client** (fluent, net/http-backed; `fiberx` holds the server-side `fiber.Ctx` helpers): one `httpx.New(...)` client per upstream service; `Client.NewRequest()` builders are single-use (second execution returns `ErrRequestReused`) and builder errors surface at the terminal verb. Non-2xx responses are **not** errors — check `Response.IsSuccess()`. Retries are opt-in via `WithRetry` and the default policy retries only idempotent methods on transport errors / 429 / 502 / 503 / 504 — a POST retry needs a custom `RetryIf`; streamed bodies (`SetBodyReader`) are never retried. `WithTransport` / `WithHTTPClient` are the wire-level seams (otel, mocks) and conflict with `WithProxy` / `WithTLSConfig` / `WithCookieJar` / `WithMaxRedirects` — validated eagerly at `New`. `RequestHook` runs after the request is fully built (final `Method()` / `URL()` / `Body()` readable, headers still mutable) — the signing hook point.
- **Request body transport-encoding is opt-in and decode-only** (`internal/middleware/body_encoding.go`, order `-750`, `/api` only): a client sets `X-Body-Encoding: base64` or `gzip+base64` so code-shaped payloads (integration adapter/envelope/auth scripts, `dry_run` bodies) survive middleboxes that false-positive on them; the middleware decodes to raw JSON, strips the header, and enforces `vef.app.body_limit` on the decoded size (413 on overrun, 400 on a bad encoding/stream) **before** the content-type guard and dispatcher run. The wire format is the encoded text as the raw body and nothing around it: a payload wrapped in double quotes is refused rather than unwrapped (`TestBodyEncodingMiddleware/QuoteWrappedBase64`), because accepting it would admit a second, undocumented format that a genuine JSON-string body could not be told apart from. That shape is not hypothetical — it is what an HTTP client produces when it hands the pre-encoded string to a library that still owns the request body's JSON serialization, and since the content type stays `application/json` (the decoded body is JSON, and the `/api` guard is on it) the library re-encodes the string. Nothing in the resulting 400 would point there, so the middleware names that case in a Warn log — storage, content-hash caches and audit only ever see the raw body. Native `Content-Encoding: gzip`/`br`/`deflate`/`zstd` requests are decompressed by Fiber itself (same body-limit guard); this middleware only adds the base64 forms Fiber does not know. The API `signature` auth covers `appID+method+path+timestamp+nonce`, **not** the body, so transport-encoding is orthogonal to it. Response direction rides the existing compression middleware (`Accept-Encoding`), so there is no custom response encoding.
- No centralized `interfaces.go` or `types.go` — if found, refactor to co-locate with related code.
- Edit tool `replace_all` replaces ALL occurrences including strings/comments — scope carefully.
- `_test.go` types: always use exported PascalCase (`TestCmd`, not `testCmd`).
- Testify suite `TearDownTest`/`SetupTest` only run between top-level `Test*` methods — NOT between `s.Run()` subtests. Add per-subtest cleanup (e.g., `defer cleanup()`) for data isolation.
- **Outbox is publish-only**: `event.Bus.Subscribe` on an event whose route resolves to the outbox transport will skip outbox (filtered via `Capabilities.PublishOnly`). Direct `outbox.Subscribe` returns `transport.ErrSubscribeUnsupported`. Subscribers must attach to the configured sink (`vef.event.transports.outbox.sink`) — `memory` for single-node, `redis_stream` for cross-process.
- **At-least-once subscriptions require `event.WithGroup("name")`**: subscribing to events whose route includes outbox / redis_stream / any `Capabilities.AtLeastOnce` transport without an explicit group returns `event.ErrGroupRequired`. The group is the Inbox dedupe scope and the Redis Streams `XGROUP` name — both must be stable across restarts.
- **Outbox sink config**: with `outbox.enabled=true && sink="memory"` the relay only dispatches in-process. If `redis_stream.enabled=true` is also set, the framework logs a start-up warning. For cross-node delivery set `vef.event.transports.outbox.sink="redis_stream"`.
- **`tx_memory` is the development transport for a shared database** (`vef.event.transports.tx_memory.enabled`, default off): it satisfies the transactional-route assertion that approval and storage make at boot (`Transactional: true`) but delivers **in the publishing process** instead of persisting a row, so nothing survives a crash between commit and delivery (`Durable: false`). The motivating problem is a team whose dev instances all point at one database: `ClaimBatch` has no owner predicate and every node runs the relay, so any node's relay may claim any node's outbox rows — the handler for A's action tends to run on B's machine. Routing to `tx_memory` keeps every event in the process that published it and drops delivery latency from the relay poll interval to zero. `AtLeastOnce: false` is what keeps dev code byte-identical to prod code: the bus only *requires* `WithGroup` on at-least-once transports and never rejects a superfluous group, so a subscriber written for an outbox route runs unchanged. `Ordered: false` — releases happen at commit time, so concurrent transactions deliver in commit order, not publish order. It is deliberately a separate transport rather than a transactional mode of `memory`: `memory` must keep declaring `Transactional: false` so a production deployment that forgot to enable the outbox still fails fast. Enabling it logs a Warn. Note the sibling lotteries a shared dev database also creates — the approval timeout scanner, the eventual business-projection worker, the storage delete worker/claim sweeper, and the durable cron claim loop are all competitive consumers too; `tx_memory` fixes only the event lane, and a database per developer is the fix that covers all of them.
- **Tracing default trusts incoming TraceID** (W3C/OTel-compatible). Use `vef.event.middleware.tracing_strict=true` at trust-boundary ingresses to switch to strict mode (incoming park under `IncomingTraceIDFromContext`, fresh ID generated for the active context).
- **Redis is opt-in**: `vef.redis.enabled` defaults to `false`. When disabled, `internal/redis.NewClient` returns `nil` and the `OnStart` Ping is skipped, so applications that never touch Redis can keep `redis.Module` in the boot sequence at zero cost. Anything that needs the client (`redis_stream` transport, `cache.NewRedis`, `security.NewRedisNonceStore`, etc.) must declare the dependency with `optional:"true"` and skip work when the client is nil. Tests that bring up a real Redis container (see `internal/testx.NewRedisContainer`) set `Enabled: true` automatically.
- **Distributed locks are lease-based and topology-selected**: inject `lock.Locker` — the DI default is `RedisLocker` when the Redis client is available, else `MemoryLocker` with a boot warning (**no cross-replica exclusion**); this deliberately diverges from the "memory default + fx.Decorate" convention because a silently-local lock breaks invariants the moment a second replica starts. `lock.WithLock(ctx, locker, name, fn, opts...)` is the primary entry: auto-renewal on, fn's ctx canceled if the lease is lost, release always runs (even when fn panics), and the returned error joins fn + release (`lock.ErrNotHeld` from release means exclusivity may have been violated even if fn succeeded). Bare `Acquire`/`TryAcquire` default to no waiting and no auto-renew (`WithTTL` 30s, `WithWait`, `WithRetryInterval`, `WithAutoRenew`); auto-renew requires `WithTTL >= lock.MinAutoRenewTTL`, otherwise acquisition returns `lock.ErrAutoRenewTTLTooShort`. `TryAcquire` at the top of a cron job is the "only one replica runs this" guard. Locks are cooperative leases (single-instance atomic Lua acquisition stores owner + assigned fencing token in the expiring lock hash, backed by one global fencing counter; token-guarded Lua releases/refreshes; **not** Redlock): acquisition, release, and refresh are idempotent across go-redis's internal client retries, and successful releases leave only a short-lived retry acknowledgement. A pause outliving the TTL can still admit a second holder, so guard must-not-corrupt state with `Lock.FencingToken()` (globally monotonic, therefore monotonic per name), idempotency, or DB constraints.
- **Monitor overview uses root-filesystem disk metrics and container-aware CPU/memory metrics** (`internal/monitor`): `SystemOverview.Disk` reports only the filesystem containing the process root (`/` on Unix, `%SystemDrive%\\` on Windows) so remote mounts, disk images, bind mounts, and sibling volumes cannot inflate host capacity; `Disk()` remains the raw partition and I/O inventory. Under a cgroup (v2 or v1) that actually limits CPU or memory, limit and usage are resolved from one effective resource scope. CPU `PhysicalCores` / `LogicalCores` retain host topology, `EffectiveCores` reports the intersection of host logical CPUs, quota, and cpuset, and `TotalPercent` becomes the share of that capacity over a complete cgroup sample (per-core breakdown dropped). Memory Total/Used become the same scope's limit/working-set (usage minus inactive file cache). No effective limit, an incomplete scoped sample, or a limit at/above the host total keeps the complete host view; process and network metrics read whatever procfs exposes.
- **Database migrations**: per-module DDL goes through `internal/sqlmigration.Run(ctx, db, Plan{Label, Kind, Scripts, ExpectedTables, Pre})`. Each module keeps its own `//go:embed scripts/*.sql` since `embed` cannot cross package boundaries; everything else is shared and `sqlmigration` is the single owner of migration infrastructure: **presence probes** (`TableExists` / `CountTables` — the active schema, `current_schema()` on Postgres, never a hardcoded `public`), **schema metadata** (`LoadTableColumns` / `LoadTableIndexes` returning the dialect-neutral `Column` / `Index` with the `ColumnKind` vocabulary; MySQL unsigned integers deliberately do not normalize to the signed kinds, prefix/partial/expression indexes never match a capability; `LoadTablePrimaryKey` returns the key column sequence — read it from there, never off `LoadTableIndexes`, since dialects expose a primary key inconsistently as an index), and **migration locks** (`WithLock(ctx, db, kind, name, fn)` — `pg_advisory_xact_lock` in a transaction / `GET_LOCK` on a pinned connection / SQLite `BEGIN IMMEDIATE` with the busy timeout suspended and Go-side context-aware retry; fn must run its DDL on the handle it receives), and the **busy-contention classifier** `IsBusyContention(err)` — the one SQLite write-lock vocabulary, trusting the driver's result code whenever it exposes one and matching the message only for drivers that expose none, so an unrelated failure cannot reclassify as contention just because a statement argument echoed "is locked" into it; the migration lock, the cron claim loop and the cron outcome-write retry all classify through it instead of keeping private copies. `Run` takes the lock automatically (name = `Plan.Label`), so concurrently booting replicas provision exactly once; module migrations must not hand-roll metadata queries against `information_schema`/`sqlite_master`, their own locking, or their own contention vocabulary. Capability *policy* stays module-local: the cron store declares its required columns/indexes and verifies them via these loaders (`internal/cron/store/migration.Verify`), and approval verifies that every `apv_*` table is keyed by `id` **and** that the three open-vocabulary `kind` columns (`apv_flow_initiator`, `apv_flow_node_assignee`, `apv_flow_node_cc`) declare at least `VARCHAR(64)` (`internal/approval/migration.Verify`). That second check exists because those columns shipped as `VARCHAR(16)`, which the framework's own 17-character `department_leader` already overflows — a flow naming it failed at the INSERT with a driver-level "value too long" that named neither the kind nor the fix, and a host kind is longer still. It is the one approval check whose remedy is a forward `ALTER`, not a recreate, so the message says so; SQLite is skipped because it does not enforce a declared bound. **`auto_migrate` decides whether missing tables get created, never whether the schema is trusted** — approval verifies on every boot either way, because `CREATE TABLE IF NOT EXISTS` accepts a pre-existing table of any shape, so provisioning proves nothing about a table something else created. A schema restored without its constraints is the motivating case: approval's writes are compare-and-set statements that assume a row is uniquely addressable (`engine.ConcludeActiveNodeVisit` fails the transaction unless its UPDATE touches exactly one row), so against a keyless table carrying duplicate ids every approval silently rolls back — an intermittent "engine bug" that a boot-time `ErrSchemaOutdated` turns into one clear error. **Every statement in a script must survive a replay**: `Run` re-executes the *whole* script the moment any one expected table is missing, so adding a table to `ExpectedTables` replays every statement against a database that already has the others. `CREATE TABLE IF NOT EXISTS` survives that; a bare `CREATE INDEX` does not — Postgres/SQLite need `IF NOT EXISTS`, and MySQL, which has no such form, must declare indexes **inline in the CREATE TABLE body** (`internal/storage/migration/migration_test.go` fences this for storage). The corollary is that a MySQL script can never add an index to a table that already exists, since `CREATE TABLE IF NOT EXISTS` skips the whole statement — plan a table's indexes when you create it. A one-time data backfill belongs in the script too, but under the dialect's conflict guard (`ON CONFLICT DO NOTHING` / `INSERT IGNORE` / `INSERT OR IGNORE`) for the same replay reason.
- **A request-derived string must be copied before it outlives the request**: the framework builds Fiber with `Immutable: false`, so `ctx.Query(...)`, `ctx.Get(...)` and `ctx.IP()` behind a trusted proxy header all return zero-copy views into the pooled fasthttp request buffer. They are the caller's data only until the handler returns; afterwards the bytes belong to whatever request reused the buffer. Anything that stores such a string past the handler — parked in a cache or session store, captured by a goroutine, or handed to an application extension point that may keep it — must `strings.Clone` it at the point it is read, once, rather than at each use. **Two values are copied by their accessor instead, so every call site is safe by construction**: `fiberx.GetIP` clones (`TestGetIP/SurvivesLaterTraffic`), and the logger middleware clones the request id on the way into the context, which is the only place the framework reads Fiber's `requestid` (`TestRequestIDSurvivesLaterTraffic`). That accessor-level copy is deliberate rather than per-site: the audit event, the login event and every event `Envelope.CorrelationID` are all built behind an **asynchronous** publish — `Bus.publishAsync` detaches the context and the worker builds the envelope long after the request returned — and a rate-limit key discarded within the request reads no differently at the call site from an audit record that outlives it. Everything read straight off `fiber.Ctx` still copies at the retention point: the trust-login gateway copies the app ID, external user ID, redirect and User-Agent it parks with a code (`TestResolverWins` — drop the clone and the identifier a `TrustUserResolver` was handed reads as the *next* request's value); `sessionMeta` and `publishLoginEvent` copy the User-Agent (`TestSessionMeta`); and the storage proxy copies the object key before handing it to `storage.FileACL`, since `url.PathUnescape` returns its input unchanged when there is nothing to unescape. Values that are immediately concatenated (nonce store keys), parsed into new allocations (`strconv`, `url.Parse` results that get re-serialized), or JSON-marshalled on the spot are already copies and need nothing.
- **The HMAC signature covers a `security.SignatureRequest`, and anything a protocol must protect belongs in `BoundParams`**: `Sign(request)` / `Verify(ctx, request, credentials)` take the app ID, method, path and caller-chosen bound parameters as one struct, with the presented timestamp/nonce/signature as the existing `SignatureCredentials`. The canonical payload is every parameter rendered `key=value` and joined by `&` **in ascending key order**, so a request with no bound parameters is byte-identical to a scheme that binds only method and path — that equivalence is pinned in `TestSignatureBoundParameters/CanonicalPayload` because third parties reimplement the string in their own language. **Bound keys and values are percent-encoded (RFC 3986 unreserved set, uppercase hex, space as `%20` — AWS SigV4's rule, deliberately neither `url.QueryEscape` nor `encodeURIComponent`); the fixed values are not.** The asymmetry is load-bearing on both sides: bound parameters are caller-supplied and a signed `redirect` routinely carries `&` and `=`, so rendered raw the payload is ambiguous — `{"x": "1&y=2", "y": "3"}` and `{"x": "1", "y": "2&y=3"}` both flatten to `x=1&y=2&y=3` and a signature minted for one verifies the other (`CanonicalPayload/DelimitersAreUnambiguous`) — while encoding the fixed values instead would change the string every third party already generates for plain API signature auth. `BoundParams` values are the **decoded** ones, never their URL-encoded wire form, and a key colliding with `app_id`/`method`/`nonce`/`path`/`timestamp` is refused (`ErrSignatureBoundKeyReserved`) rather than silently shadowing a fixed field. The rule of thumb: a parameter a signed link carries that is *not* in `BoundParams` is attacker-controlled — an unsigned `user_id` on the trust-login handoff is a complete authentication bypass, which `TestTamperedHandoff/SwappedUserID` exists to catch (it swaps in a second user this system really has, so the request fails verification rather than merely failing to resolve).
- **A route outside `/api` has no principal unless it authenticates itself**: `internal/api/middleware.Auth` is the only thing in the framework that ever calls `contextx.SetPrincipal`, and it runs inside API operation dispatch only. Every `app.Middleware` that registers a real route — the push handshake, the MCP handler, the integration inbound gateway, the storage download proxy — must therefore dispatch `security.AuthManager` itself; reading `contextx.Principal(ctx)` there returns nil forever, which is exactly how the proxy handed every `storage.FileACL` a nil principal behind a valid `Authorization` header. The framework's own defaults hid it: `DefaultFileACL` decides purely on the key prefix and never reads the principal, so nothing failed until an application supplied an ACL that does. The proxy (`GET /storage/files/<key>`) resolves identity **only for non-`pub/` keys**, from `Authorization: Bearer` or `?__accessToken=` (a browser cannot set a header on `<img src>` or a download link, the same reason push accepts it) — authenticating the `pub/` branch would buy nothing, since it never reaches the ACL, and would let an expired token in a long-lived tab break public image loading. A request with **no** credential reaches the ACL as nil rather than being rejected (the ACL is the authority and may grant an anonymous read); a credential that is present but **invalid** is rejected, so an expired token does not surface as an opaque access-denied.
- **Uploaded files are recorded in a durable registry** (`sys_storage_file`, public model `storage.FileRecord`, read surface `storage.FileRegistry` via DI): the claim row is deleted the moment a business transaction adopts the file, taking the original filename with it, so the registry is what makes a stored key nameable afterwards. The record is a **projection of the claim** — every field is copied from it — which is what lets both finalize paths write it identically. It is written as a side effect of the claim's `pending → uploaded` compare-and-set inside `internal/storage/store/claim_store.go` (`MarkUploaded` for `complete_upload`, `MarkUploadedIfPendingExpired` for the sweeper's recovery branch), never at the call sites, so "a claim became uploaded" and "a file record exists" stay one fact in one place; there is deliberately **no conflict clause** on the insert (on MySQL `ON CONFLICT DO NOTHING` compiles to `INSERT IGNORE`, which would swallow every error, and the two CAS predicates are mutually exclusive so a duplicate means the invariant is already broken). `Consume` flips the record to `claimed` **best-effort** — the claim table, not the registry, authorizes adoption, and a file uploaded before this table existed must not fail the business write — and the delete worker's success transaction flips it to `deleted`, first-writer-wins (one key legitimately carries several queue rows) and never from the dead-letter path (the object is probably still there). `status` is `uploaded` (recorded, unreferenced) → `claimed` → `deleted`; `started_at` is the upload-session start, the only instant both write paths agree on, while `created_at` is when the row was written (recovery can trail the real completion by the whole claim TTL). The download proxy resolves each key through the registry to serve an RFC 6266 `Content-Disposition`, and `sys/storage/file.resolve` is the client-facing batch lookup, ACL-gated per key exactly like the proxy. Reclaiming files that were uploaded and never adopted is opt-in via `vef.storage.orphan_retention` (0 = off, so an upgrade never starts deleting user data on its own).
- **Storage events require a transactional route**: `vef.storage.file.claimed`, `vef.storage.file.deleted`, and `vef.storage.delete.dead_letter` are all published with `event.WithTx(tx)` so the events become visible iff the originating business transaction commits. The storage module fails fast at start-up (via `event.RouteInspector`) unless these patterns resolve to a `Transactional=true` transport. Required config:
  - `vef.event.transports.outbox.enabled = true`
  - a routing rule with `pattern = "vef.storage.*"` → `transports = ["outbox", "memory"]`, **or** set `vef.event.default_transport = "outbox"`.
  The second entry is `vef.event.transports.outbox.sink` (`memory` single-node / `redis_stream` cross-node) and it must be **listed in the route**, not just configured — see the subscribable-route gotcha. Subscribers must supply `event.WithGroup("...")`.
- **Approval events require a transactional route**: every `approval.*` event except `binding_failed` is published with `event.WithTx(tx)` (via `EventPublishBehavior` in the CQRS pipeline and `engine.PublishEventsTx` from the timeout scanner). The approval module fails fast at start-up (via `event.RouteInspector`) unless those event types resolve to a `Transactional=true` transport. Business projection is driven by durable desired state, not lifecycle-event delivery, so an outbox-only route is sufficient for the framework itself. Required config:
  - `vef.event.transports.outbox.enabled = true`
  - a routing rule with `pattern = "approval.*"` → `transports = ["outbox", "memory"]`, **or** `vef.event.default_transport = "outbox"`.
  The second entry is `vef.event.transports.outbox.sink` and it must be **listed in the route** — see the subscribable-route gotcha; drop it only for a deployment that publishes approval events without consuming them in-process. The projection worker emits `InstanceBindingFailedEvent` only as an operator notification after persisting the failed attempt; it first uses a short `db.RunInTx` + `event.WithTx(...)` and falls back to a plain publish on `event.ErrTxRequired`. Host subscribers must supply `event.WithGroup("...")` when the route includes an at-least-once transport.
- **An outbox-bearing route must list the sink, or nothing can subscribe to it**: the outbox is `PublishOnly`, so `Bus.Subscribe` strips it from the resolved route and needs something left to attach to. A route of `transports = ["outbox"]` (or `default_transport = "outbox"` with no rule) therefore publishes and relays perfectly — the boot-time transactional-route check passes, rows land in the outbox, the relay dispatches them into `outbox.sink` — while **every** `Subscribe` / `event.SubscribeTyped` / `approval.SubscribeInstance` / `approval.BindCommand` against it fails with `event.ErrNoRouteMatched`. A host that does not propagate that error observes its subscribers silently never firing, which reads as "the framework never emits this event". Fix: name the sink in the route (`["outbox", "memory"]`). `validateOutboxSinkRoute` hard-fails only the *mismatch* case (a route with some other subscribable transport while the sink is a different one, where subscribers would attach to the wrong transport) and **warns** on the outbox-only case, because publishing without in-process subscribers is a legitimate deployment — `unsubscribableOutboxOrigins` is the tested classifier behind that warning.
- **Approval domain events are published in occurrence order, and every producer must emit at the moment the event occurs**: the request-scoped `EventCollector` is one ordered buffer written by three producers — the command handler, `NodeService`, and the engine's recursive traversal — and the engine emits from deep inside the call the handler makes. A handler that accumulates its own events in a local slice for one `Add` at the end therefore lets the engine's events overtake them: that is how `approval.instance.completed` used to reach subscribers *before* the `approval.task.approved` that caused it, and before the `approval.instance.created` of an auto-completing instance. `behavior.EmitEvents(ctx, bus, db, ...)` is the single emission entry point (collector inside the CQRS pipeline, transactional publish outside it, e.g. the timeout scanner) — use it, and call it where the event happens. `HandleNodeCompletion` emits its own cancellations and rejection completion before advancing; its **return value is suppression input only** (`SuppressSupersededActivations`), so re-adding it to the collector double-publishes. `internal/approval/command/event_order_test.go` fences both the order and the exactly-once property.
- **Same-applicant policy is per-seat, keyed on the resolved actor**: `sameApplicantAction` applies whenever the applicant holds a seat in a node's resolved assignee set (post-delegation actor ID), not only when they are the sole approver. `auto_pass` clears the applicant's own task — at node entry, or when a sequential queue reaches their seat (the `ActivateNextSequentialTask` cascade) — and the entry-time sweep then evaluates the pass rule like a manual action would, concluding the node outright when it is satisfied (superseded seats are canceled; the same evaluation now applies to consecutive-approver auto-pass). `exclude` (避嫌) removes the applicant's seat so only the remaining approvers decide, with pass rules counted over the remaining set; an exclusion that empties the set falls back to `EmptyAssigneeAction` verbatim. `transfer_superior` replaces only the applicant's seat. Tasks a human explicitly creates afterwards (add-assignee splices, transfer, reassign, timeout auto-transfer) are exempt — an explicit decision to involve the applicant overrides the node policy. Entry-time completions still never fire timing-based node CC, uniform with all entry-time auto-pass paths.
- **To-do notifications subscribe to `TaskActivatedEvent`, never `TaskCreatedEvent`**: a sequential node inserts every assignee's task up front (first `Pending`, rest `Waiting`), so `TaskCreatedEvent` means "the row exists", not "act on it" — notifying on it pages approvers whose turn has not come. `TaskActivatedEvent` is the single answer to "whose turn is it now" and fires for every way a task starts waiting on someone: created already pending, promoted from `Waiting` when the queue advances, handed over by transfer or timeout auto-transfer, or reassigned — `TaskActivationReason` (`assigned` / `queue_advanced` / `transferred` / `reassigned`) says which. Subscribing to it alone is sufficient; do not enumerate the actions that can produce a pending task. `TaskTransferredEvent` / `TaskReassignedEvent` remain the record of the *act* (they name both parties, so they are what tells the outgoing assignee their task moved on). Deliberately not derivable from `TaskCreatedEvent.Deadline`: a task's deadline is nil whenever its node sets no `timeout_hours`, so nil cannot distinguish queued from actionable.
- **Programmatic flow control goes through `approval.Service`, and the API resources are its first callers**: all 15 runtime operations — every write `approval/instance` and `approval/admin` expose, including `RetryBusinessProjection` — are methods on the public `approval.Service` (`approval/service.go`, inputs `approval.<Op>Input`), implemented by `internal/approval/facade` as one `cqrs.Send`. `InstanceResource` and `AdminResource` call the same interface, so the HTTP path is itself a programmatic caller and cannot diverge from a host routine; `AdminResource` keeps `cqrs.Bus` for its **queries only**, and a new runtime operation must not reuse that seam. Hosts inject `approval.Service` (available whenever `vef.ApprovalModule` is on) — never reach for `cqrs.Bus` + the `internal/approval/command` types, which are unreachable from another module anyway and, called directly, would bypass the collector behaviors that publish events and write audit rows. **Read the full contract on `approval.Service` itself** — the handle-is-the-transaction-boundary rule, the context rule, the audit-operator recipe and the trust inputs all live in that doc comment; only what a reader would not find there is repeated here.
  - **The commands embed the public inputs** (`command.ApproveTaskCmd struct { cqrs.BaseCommand; approval.ApproveTaskInput }`), so the facade forwards with one compiler-checked assignment. Add a field to the `Input` and both sides have it; there is deliberately no field-by-field copy and no parity test to keep in sync. Go 1.27 promoted-field literals keep `command.ApproveTaskCmd{TaskID: …}` and `cmd.TaskID` working unchanged, which is what let this land with zero call-site edits.
  - **The Service does not authorize.** The RBAC tokens gating the endpoints (`approval.instance.terminate`, `approval.task.reassign`, `approval.binding.retry`) live on the `OperationSpec`s; the commands behind them check only the tenant scope in `Caller`. A host exposing `TerminateInstance`, `ReassignTask` or `RetryBusinessProjection` through its own surface owns that check — the call site looks identical to the framework's own, so nothing flags the omission.
  - **A nil handle is refused with `approval.ErrDBRequired`, and a `fiber.Ctx` is unwrapped before binding** (`facade.bindDB`). Both are caller mistakes the compiler allows and that used to fail silently: a nil handle let `TransactionBehavior` fall back to its own primary handle (operation outside the caller's transaction, audit rows attributed to `orm.OperatorSystem`), and `contextx.SetDB` mutates a `fiber.Ctx`'s Locals **in place**, so binding onto one left the whole request pointing at a transaction that dies at the caller's commit (`TestServiceUnwrapsFiberContext`).
  - **Pass the context `RunInTx` hands the callback, not the outer one.** `RunInTx` does put the `orm.OnCommit` registry on the callback context, and the `tx_memory` transport publishes exclusively through it — so with the outer context every approval action on a `tx_memory` route fails with `orm.ErrNoCommitScope` and rolls back. The audit operator likewise binds **before** the transaction (`db.WithNamedArg(orm.PlaceholderKeyOperator, userID).RunInTx(…)`), because `WithNamedArg` panics on a tx-scoped handle.
  - **The outward error sentinels and codes are public for the same reason**: `approval/api_errors.go` holds every `approval.Err*` `result.Error` and `approval.ErrCode*` (moved out of `internal/approval/shared`, which keeps only the `ErrMessage*` i18n keys its internal builders template), so a host can `errors.Is(err, approval.ErrFlowNotActive)` on what the Service returns instead of comparing numeric codes. `approval.ValidateBusinessIdentifier` returns that same `result.Error` sentinel directly. Plain non-API sentinels (`ErrDBRequired`) live in `approval/errors.go`, matching `event`/`datasource`.
  - Flow-definition commands (create / deploy / publish / update / toggle) are deliberately outside the contract: design-time administration, different trust posture, served by the `approval/flow` resource.
- **The approval CQRS collectors are re-entrant, and the outermost dispatch owns the flush**: `approval.Service` is the first host-callable way to re-enter the command pipeline from *inside* a running command — an `InstanceLifecycleHook` fires in-transaction and may itself act on another task. `installCollector` therefore **reuses** a collector already on the context and declines ownership, mirroring how `TransactionBehavior` joins an already-open transaction rather than nesting a second one; a fresh inner collector would flush the inner command's events and action logs the moment its handler returned, publishing an effect ahead of the cause that produced it (the exact inversion the occurrence-order rule exists to prevent, and one `event_order_test.go` cannot see because it only exercises single-level dispatch). A failed dispatch unwinds only what *it* appended (`Collector.truncate` against an entry mark, the same shape as `runInTx`'s savepoint hook unwinding), so an enclosing command that swallows the inner error keeps its own items and drops the ones describing writes that did not happen. `TestCollectorBehaviorReentrantDispatch` fences both properties.
- **Host subscriptions use `approval.SubscribeInstance`**: the declarative wrapper over `event.SubscribeTyped` for instance events. Handlers receive the event plus its delivery `Envelope` — `Envelope.ID` is the Inbox dedupe key, stable across redeliveries, the key for manual idempotency on at-least-once routes. Routing filters are data, not predicates — `approval.ForFlows(...)` / `ForTenants(...)` (OR within a filter, AND across filters); non-matching events are acked without invoking the handler. Business predicates (final status, form values) stay in the handler body. The consumer group derives from the handler's method identity (`vef:sub:<module-relative pkg>.<Type>.<method>`, mirroring the `vef:default:<uuid>` shape); anonymous handlers fail with `ErrAnonymousSubscriberGroup` unless `approval.WithGroup` is given, and a duplicate derived group in one process fails with `ErrDerivedGroupConflict`. **Renaming/moving a handler changes its derived group** (new XGROUP, orphaned old one) — pin with `WithGroup` before such refactors. `approval.NewFilteredLifecycleHook(hook, filters...)` applies the same filter vocabulary to `InstanceLifecycleHook` registrations.
- **Complex business linkage has two lanes, both outside the projection**: `approval.BindCommand[E, C](bus, commands, mapper, opts...)` bridges one instance event type into a host CQRS command — the mapper is a pure translation over `(evt, env)` (`ok=false` acks without dispatching; copy `env.ID` into the command when the handler needs a dedupe key), the command handler owns the business logic and its result is discarded, and the consumer group derives from the **command type** (`vef:cmd:<module-relative pkg>.<Type>`; duplicate default binding fails with `ErrDerivedGroupConflict`, unnamed/interface command types with `ErrUnnamedCommandType`, query types with `ErrNonCommandAction`). Handlers must be idempotent under at-least-once routes. Unlike the eventual projection (which converges on the latest state and may skip intermediate statuses), every transition dispatches its own command — use BindCommand for effects tied to a specific lifecycle moment, and `InstanceLifecycleHook` (`OnInstanceCreated` + `OnInstanceTransition(ctx, db, instance, from, to)`, both in-transaction; the transition hook fires on **every** state-machine transition after the engine projection, final-state logic checks `to.IsFinal()`) for invariants that must commit or roll back with the approval action.
- **Orphaned consumer groups are observable and reclaimable**: `sys/monitor.get_event_streams` reports every redis_stream stream + group (consumers / pending / lag / last-delivered) via the optional `event.StreamInspector`; a group with growing lag and only idle consumers is a decommissioned subscriber's leftover. Opt-in reclamation: `vef.event.transports.redis_stream.idle_group_retention` (0 = off) destroys groups with no pending entries whose every consumer record has been idle beyond the window — groups with pending entries or no consumer record at all are never touched, and the sweeper (interval `idle_group_sweep_interval`, default 10m) always skips this process's own subscriptions.
- **Business write-back is a version-pinned desired-state projection**: a business-bound flow carries one `BusinessBindingConfig` (`businessBinding`) with `TableName`, one or more `KeyColumns`, mandatory `StatusColumn` + `InstanceIDColumn`, optional `StartedAtColumn` / `FinishedAtColumn`, and optional `StatusMapping`. Save-time validation uses `schema.Service` to require the key columns to exactly match a complete, non-null PK or UNIQUE constraint (partial/expression indexes do not qualify), verifies every column exists, and rejects all key/write-column overlap. Deploy snapshots the normalized binding onto `FlowVersion`; editing `Flow.businessBinding` only affects the next deployed version. `BusinessRefResolver.ResolveRecordKey` returns values for exactly those key columns; the default accepts a bare single-column ref or a composite JSON object.
  One `apv_business_projection` row owns each physical `(table, record key)` target and stores the latest complete desired state, desired/applied revisions, desired/applied owner IDs, retry state, and the binding/key snapshots. Every instance status transition goes through the projector; a non-final owner blocks a second approval, a final owner may be superseded, and the business table's instance-ID column is the compare-and-set fence that prevents stale instances/workers from overwriting the new owner. Config `vef.approval.business_binding.consistency` defaults to `synchronous`: the business row is written in the approval transaction and any failure rolls the approval action back. Setting it to `eventual` commits only desired state; the lease-based worker (`scan_interval` default 10s, `batch_size` default 100) repeatedly applies the newest revision with exponential backoff and no retry limit. Lifecycle events are notifications only and never drive convergence. Each write projects the full configured state: mapped/current status, owner instance ID, original start time, and final finish time (or NULL while non-final).
- **Who may start a flow is a two-state setting, enforced as mutually exclusive**: `Flow.IsAllInitiationAllowed` and the `apv_flow_initiator` rules are never both meaningful — `start_instance` short-circuits on the flag and only consults the rules when it is false, and `CheckInitiationPermission` fails closed on an empty rule set. Create/update therefore reject both incoherent pairings (`validateInitiatorPolicy`): rules alongside open-to-everyone (`ErrInitiatorsNotAllowed`, 40022 — they would render as a restriction that does not hold) and a restricted flow with no rules (`ErrInitiatorsRequired`, 40023 — nobody could start it). That makes the stored state a bijection, which is the point: **`find_initiators` returning an empty list means exactly "open to everyone"**, so one query answers who may start a flow. It returns `[]`, never `null` — a nil slice would serialize as `null` and read as "unknown" instead of an answer. A React flow editor must mirror the exclusivity (disable the initiator editor while the open-to-everyone toggle is on, and require ≥1 rule otherwise) rather than relying on the server to reject the save.
- **Approval node config normalizes at deploy**: `NodeData.ApplyTo` resolves omitted enum fields to designer defaults (the `approval.Default*` constants in `node_data.go`, including `DefaultUrgeCooldownMinutes`), and the default-true permission toggles (`IsRollbackAllowed`, `IsTransferAllowed`, `IsAddAssigneeAllowed`, `IsRemoveAssigneeAllowed`, `IsManualCCAllowed`) are `*bool` so an omitted field resolves to allowed while explicit `false` survives. Deploy validation (`service/node_config_validation.go` + `flow_definition.go`) rejects out-of-enum values, incomplete dependent fields (ratio rule without `passRatio`, `transfer_specified` without `fallbackUserIds`, `transfer_admin` without `adminUserIds`, `specified` rollback without `rollbackTargetKeys`, blank condition subjects/expressions, structurally-empty conditions — a non-default branch needs ≥1 condition group, and any group present on any branch needs ≥1 condition, since the engine treats empty as an unconditional match), invalid `AddAssigneeTypes` entries and `parallel` add-assignee on sequential nodes (a sequential queue has no parallel lane; the add-assignee command also splices `before`/`after` additions into the queue at the anchor's position, keeping exactly one Pending task), duplicate non-default branch priorities ("first match wins" needs a total order; the engine also tiebreaks equal priorities by branch ID), dangling/self/non-task `rollbackTargetKeys` references, and `auto_reject` on handle nodes (execution type and timeout action — handle nodes do work, they don't decide; the timeout scanner finishes a timed-out handle task as `handled`, never `approved`). `ValidateFlowDefinition` returns the parsed node data that deploy then persists — never re-parse. `PassRatio` uses a single storage convention: a percentage in `(0, 100]`, consumed verbatim by the engine (no fraction form). Form schemas are split at deploy: `apv_flow_version.form_schema` stores the host-owned designer document as semantically equal JSON — the jsonb column normalizes formatting and key order; numeric precision is preserved (opaque `json.RawMessage`; detail APIs return `formSchema` the same way), and `form_fields` stores the flat `[]approval.FormFieldDefinition` derived once at deploy through the injected `approval.FormSchemaParser` (built-in: the vef-framework-react form-editor parser in `internal/approval/formeditor`; hosts replace it wholesale with `vef.ProvideApprovalFormSchemaParser`) — framework consumers (form-data validation, storage-table DDL, aggregate checks) read `form_fields` only. A selection field whose options the projection could **not** enumerate carries `FormFieldDefinition.OptionSource` instead — the post-dereference descriptor of a remote source (`resource` / `action` / `version` / `params` plus the label/value `mapping`), so a consumer never chases a `dataSourceId`. The framework never resolves it: select validation reads `Options` and accepts any value when there are none, and the descriptor exists purely for consumers that must render a stored value as its label. It rides on the field rather than a side channel so a detail-table column carries its own through `Columns`. Whether one call can translate a whole column is **not** a given: a request parameter is a `DynamicParam`, either a literal or an expression bound to the live form (what makes a cascading select work), and the framework carries them **unevaluated** because it holds no form values to evaluate them against. `RemoteOptionRequest.HasBoundParams` is the question to ask — false means one lookup serves every row, true means the option set is per-row and a list-translating consumer must evaluate per row or leave that column untranslated. The parsed fields are validated at deploy too (`ValidateFormFields`: unique keys, known kinds, compilable patterns, coherent bounds; a `table` field needs ≥1 column, columns must not nest another table, column keys are unique per table, scalar fields must not declare columns, and a remote `optionSource` must name a resource and an action — a source resolving nowhere fails at deploy rather than silently rendering raw values in every consumer), and `InstanceTitleTemplate` is parse-checked at flow create/update. Aggregate field conditions (`Condition.Aggregate` sum/count/avg + `Column`) are validated twice: structurally in `validateCondition` (numeric comparison operators only, count forbids / sum-avg requires a column — the rule derives from `AggregateKind.FoldsColumn`; kind registration is deliberately NOT checked here, hosts add aggregators) and cross-schema in `ValidateConditionAggregates` at deploy (kind registered against the boot aggregator set; subject is a table field; the column exists and is a number field). Field conditions evaluate natively in Go against the `approval.ConditionOperator` contract; `applicantId` / `applicantDepartmentId` are reserved subjects resolved from the instance context and shadow same-named form fields, as do host-supplied globals (see the globals bullet). Expression conditions run through the framework `expression.Engine` (expr-lang backend; syntax `formData.field`, `and` / `or` / `not`). The flow editor mirrors the defaults (`normalize-node-data.ts`), the validation (`flow-validation.ts`), and the operator vocabulary (shared from `@vef-framework-react/expression`); the two sides must stay in lockstep.
- **Who may approve, who gets copied, and who may start are three open registries, all descriptor-driven**: `approval.AssigneeKind`, `CCKind`, and `InitiatorKind` carry the built-in constants but no `IsValid` — the deployable kinds are exactly those with a registered resolver. A host adds one by implementing the public contract (`approval.AssigneeResolver` / `CCResolver` / `InitiatorResolver`, each a `Describe() KindDescriptor[K]` plus its own verb: `Resolve` → `[]ResolvedAssignee`, `Resolve` → recipient IDs, `Permits` → bool) and registering it with `vef.ProvideApprovalAssigneeResolver(...)` / `...CCResolver(...)` / `...InitiatorResolver(...)`. A resolver whose kind matches a built-in **replaces it in place** (keeping the designer's option order); any other kind is appended, in ascending kind order — the JS-lib override semantics, implemented in `strategy.overlayKinds` rather than left to fx group ordering, which is not a contract. That sort is load-bearing rather than tidiness: an fx value group arrives randomized, so appending in arrival order reshuffles the designer's dropdown on every restart, and it is why two host resolvers claiming one kind are refused at boot (`errDuplicateHostKind`, naming the kind) instead of resolving last-wins — with a randomized group, "last" is a per-boot coin flip over which resolver actually assigns work. Overriding a built-in is unaffected: that is one host registration matching a framework kind. The composites are built in `internal/approval/strategy/module.go` from `Builtin*Resolvers(svc)` overlaid with the host group, so "which one wins" is deterministic.
  The `KindDescriptor` — kind, label, `SelectionMode` — is the load-bearing piece: **one declaration drives what the designer collects and what save-time validation requires**, which is what makes a host kind validated like a built-in with no framework change. `SelectionNone` is the shape most hospital-style rules want ("the applicant's head nurse", "科主任"): no designer input, resolved from `NodeResolveContext` at run time; `SelectionCustom` is the "expert panel" shape, IDs picked through a host-registered picker keyed by the kind's own name. `shared.CheckKindRule` is the single place a mode becomes a requirement (unknown kind / IDs required / form field required), consumed by deploy validation (`FlowDefinitionService.validate{Assignee,CC}Definitions`, vocabularies injected from the composites) **and** by flow save (`validateInitiatorRules`, which merged the old `validateFlowEnums` + `validateInitiatorPolicy`; a parameterless initiator kind legitimately carries no IDs, so the "every rule needs IDs" check is now per-descriptor). Note the ordering that follows: an open-to-everyone flow carrying rules is refused as incoherent *before* any kind is examined. `approval/flow.list_kind_options` serves all three catalogs — read straight off the boot-registered resolvers, labels resolved per call so they follow `VEF_I18N_LANGUAGE` — and is what the React designer's dropdowns and `flow-validation.ts` consume (`EditorPlugins.assigneeKinds` / `ccKinds`, `BasicStep.initiatorKinds`, `FlowValidationContext`); omitting it falls back to the built-in catalogs, which silently reports a host kind as an unknown type, so a host that registers kinds must pass the served list. Two constraints are enforced at boot rather than discovered later: a faulty descriptor (blank kind or label, out-of-enum mode) fails `overlayKinds`, and an **initiator** kind may never be `SelectionFormField` — initiation is checked before an instance, and therefore before a form, exists. `InitiatorResolver` is deliberately a membership predicate rather than a people-producer, for the same reason `RoleMembershipChecker` exists: enumerating everyone a role admits does not scale. Assignee and CC resolution share `approval.NodeResolveContext` (the live `*Instance` and `*FlowNode` plus the in-flight `FormData` and the `UserInfoResolver`) so a kind written for one side works verbatim on the other; CC deliberately does not see `CCTiming`, which is the engine's schedule, not a resolver's business. CC stays best-effort at the `CompositeCCResolver.CollectUserIDs` boundary — an unresolvable rule is logged and skipped, never rolling back the approval that triggered it — while an unregistered **initiator** kind is a loud error, since treating it as "denied" would read as a permission bug instead of a configuration one.
- **Condition routing reads host-defined globals, resolved server-side and snapshotted**: beyond form data and the two applicant subjects, a flow can branch on host variables — tenant attributes, applicant roles, business limits. The host implements `approval.InstanceGlobalsResolver` (`Resolve(ctx, principal, flowCode) (map[string]any, error)`, public `approval` package) and registers it with `vef.ProvideApprovalGlobalsResolver(...)`; the framework default resolves nothing. `InstanceResource.Start` calls it **before** dispatching the command, and `StartParams` deliberately has no globals field: globals steer condition branches, so an applicant able to supply them could steer their own approval. The result is persisted onto `Instance.Globals` (`apv_instance.globals`, jsonb), which makes routing deterministic across re-evaluation — like `ApplicantDepartmentID` it describes the world at initiation, not live state, and resubmit does not re-resolve. Consumption is one construction site (`internal/approval/engine/condition.go`): **field** conditions resolve a subject applicant-subjects → globals → form data (so a global shadows a same-named form field), **expression** conditions bind each entry as a top-level name (the built-in `formData` / `applicantId` / `applicantDepartmentId` are assigned last and win a collision), and **aggregate** field conditions deliberately skip globals since they fold a detail table and globals are scalars by contract. Deploy validation cannot check a global's name — it is runtime data, and a field-condition subject that names no global falls through to form data — so the designer's allow-list is the practical guard: `EditorPlugins.globalSubjects` in `approval-flow-editor` offers them between the built-in applicant subjects and the form fields, mirroring the same shadowing order. `vef.ProvideApprovalGlobalsResolver` composes through `fx.Decorate`, so a resolver that needs `orm.DB` or any other dependency declares it as a constructor parameter (`TestGlobalsResolverOverride` pins the whole chain end to end).
- **Approval field permissions**: a node's `fieldPermissions` map keys a top-level form field to `visible` / `editable` / `hidden` / `required`; an absent key means `visible`. The viewer-scoped projection in `my.get_instance_detail` (`query/field_permissions.go`) max-merges the lattice (`hidden < visible < editable < required`) over the viewer's participation contexts (own task, a task delegated away, CC delivery, applicant), granting write strength (`editable` / `required`) only from a Pending task the viewer themselves holds or a resubmittable applicant and clamping every read-only context to `visible`; `hidden` values are stripped from the returned `formData`, and a viewer with no recognized context sees nothing (fail-closed — the participant set behind `IsInstanceParticipant` — applicant, any task's `assignee_id` at any status, any task's `delegator_id`, CC recipient — MUST stay a subset of the contexts the resolver recognizes, else the failure mode is "sees nothing"; the delegator leg is what makes the person whose slot a delegation reassigned able to watch it). **`IsUrgeAuthorized` is that same set minus CC** — both read one `isDecisionParticipant` predicate, so a participant admitted to the detail may also urge unless they are a mere observer: the applicant plus anyone a task was ever opened on, whether they still hold it (`assignee_id`, any status) or handed it to a delegate while the slot stayed theirs (`delegator_id`). Transfer needs no leg of its own — it opens a new task on the transferee and leaves the original row's `assignee_id` intact. The right is instance-scoped, not task-scoped (urge any pending task, not only your own; the per-`(task, urger)` cooldown is what bounds volume), and CC recipients are excluded because observers abused it. `computeActions` mirrors the same predicate so the offered `urge` action cannot drift from what `UrgeTaskHandler` accepts. The write path validates the submitted editable subset via `validateFormField` and enforces `required` must-fill on approve / handle only (reject / transfer / rollback stay exempt; a permission-less node loads no `form_fields` and drops any submitted data). Deploy validates permission keys against the form fields, enum validity, the CC `visible` / `hidden` subset, and rejects a `required` permission on a node whose timeout action resolves to `auto_pass` (the timeout scanner's auto_pass finishes tasks without the required check). The React designer mirrors these checks in `flow-validation.ts` — keep the two in lockstep.
- **The approval form payload is capped, and the cap is host policy**: `vef.approval.form_data_max_bytes` (default 64 KiB, `config.DefaultFormDataMaxBytes`) bounds the JSON-encoded `formData` and is enforced two ways — `ValidationService.ValidateFormData` applies the **absolute** cap at start / resubmit, where the applicant owns the whole payload, while `TaskService.PrepareOperation` applies it to the **growth** an approver's edit introduces, so an instance already over the cap (raised then lowered, or predating it) stays actionable instead of wedged. Violations are `approval.ErrFormDataTooLarge` (i18n `approval_form_data_too_large`). The default is generous for a field-based form but **not** for detail tables carrying thousands of rows — a scheduling roster or itemised settlement is legitimately larger, and that is what the setting is for. Size it against the real cost rather than raising it blindly: each submission is held in memory as a decoded map, stored on `apv_instance.form_data`, and copied to `apv_form_snapshot` on every node traversal, so one instance costs roughly the payload times the nodes it passes; on Postgres `form_data` also carries a GIN index. `vef.app.body_limit` (default 32 MiB) is the outer ceiling, so a cap above it can never be reached. The services take the cap through `service.WithFormDataMaxBytes` and `internal/approval/service/module.go` resolves it from config — a non-positive value falls back to the default, never to unbounded.
- **Approval detail tables are single-level with SQL-like aggregates**: `FieldTable` fields hold a list of row objects shaped by `Columns` (nesting is rejected at deploy — deep structures belong to business tables reached via the business binding); on the table field itself `Validation.MinLength/MaxLength` bound the row count and `IsRequired` means ≥1 row. Field-condition aggregates fold detail tables through registered `approval.Aggregator` implementations (FX group `vef:approval:aggregators`, host-extensible via `vef.ProvideApprovalAggregator`; boot fails if a built-in kind is unregistered): count folds rows, sum over an empty table is 0, avg over an empty table matches nothing (SQL NULL semantics), nil cells are skipped, and a non-numeric cell fails the evaluation loudly. In StorageTable mode every table field projects into its own child table `apv_form_<versionID>__<sanitized fieldKey>` (`id`/`instance_id` indexed non-unique/`row_index`/columns/`created_at`), written replace-never-append alongside the main row; `apv_form_table` registers every physical table with `source_field_key` ('' = main table, `(version_id, source_field_key)` unique). The React designer must mirror the table-field rules, the aggregate vocabulary, and the aggregate validation.
- **Approval paused instances have closing paths**: the instance state machine allows `Returned→Withdrawn` (applicant abandons instead of resubmitting), `Returned→Terminated`, and `Withdrawn→Terminated` (admin cleanup) in addition to the resubmit transitions — paused instances must never be strandable. `TerminateInstanceCmd` and the my-detail `availableActions` both derive from `engine.InstanceStateMachine` rather than hard-coded status checks; keep new lifecycle features on that pattern.
- **Approval visit trail is the traversal source of truth**: the engine records one `apv_node_visit` row per node traversal — begun in `FlowEngine.ProcessNode` (the single activation choke point) and concluded by whichever path decides the node (`handleProcessResult` for continue/complete kinds, `HandleNodeCompletion` for pass/reject, `AdvanceCCNodeIfAllRead` for read-confirm CC, rollback → `returned`, withdraw/terminate → `canceled` via `engine.CancelActiveNodeVisits`). **Every task binds to exactly one visit** — `apv_task.visit_id` is NOT NULL and `Task.VisitID` is a plain string; task-creation paths outside the engine (transfer / add-assignee / timeout auto-transfer) inherit it from the task they replace or extend, and test fixtures that insert tasks directly must create the visit too (each test package has an `ensureActiveVisit`-style helper). There is no legacy fallback anywhere: a path that requires an executing node and finds no open visit fails loudly (`engine.ErrActiveVisitNotFound`; `ConcludeActiveNodeVisit` asserts exactly one row). Pass-rule counting is visit-scoped: `EvaluateNodeCompletion` and the remove-assignee simulation (`CanRemoveAssigneeTask`) count only the open visit's tasks, so decisions left behind by an earlier traversal (an approval that survived a peer-initiated rollback) never contaminate a redo round.
- **Approval detail projections share one assembly**: `internal/approval/query/visit_index.go` builds the `visitIndex` (visits by node, tasks by visit, finisher-log index, activities per visit — including the submit/resubmit zipped onto start visits — CC recipients per visit, instance milestones); `buildInstanceTimeline` and `buildInstanceFlowGraph` are both thin readers of it, so the two views cannot disagree. **The timeline skips `condition` visits but keeps `end` ones** — the asymmetry is deliberate: a branch routes without anything to narrate, while the end visit is the *only* signal that an instance finished by passing (approval writes no milestone log the way withdraw/terminate do, and a rejection stops on the approval node with a `rejected` visit instead of traversing to the end), so dropping it leaves an approved instance's last entry indistinguishable from a node that merely passed on the way to the next one. `TimelineEntryKind` therefore carries `end` but never `condition`; the flow graph, being the definition's full picture, keeps every node. The shared per-node payload types live in `approval/node_view.go` (`NodeParticipant`, `CCRecipient`, `Activity` + `ActivityUrge`; people are always `approval.UserInfo`); a flow-graph node's data mirrors the timeline entries of the same node (participants / ccRecipients / activities aggregated across its visits in traversal order, plus startedAt/finishedAt). **Sharing stops at the React Flow boundary**: the graph's outer structure — nodes `{id, kind (client converts to React Flow's `type`), position, data}`, edges `{id, source, target, sourceHandle}` — is React Flow's contract verbatim and must never absorb timeline structures; shared types appear only inside the node `data` payload. `formSchema` sits at the detail top level beside `flowGraph` — both are version-pinned definition snapshots (`formSchema` is the host designer document, returned verbatim), while `instance` carries runtime state only.
- **Approval persists person snapshots, not bare ids**: `approval.UserInfo` — the single person shape — carries optional `departmentId`/`departmentName`, and every place a person is recorded (task assignee + delegator, CC recipient, urge parties, action-log operator + transferee) snapshots all four fields at action time — hosts opt in by filling departments in `UserInfoResolver.ResolveUsers`. Action-log person lists (`added_assignees`, `removed_assignees`, `cc_users`) are single jsonb `UserInfo` object arrays — never parallel id/name arrays. API projections expose people as nested `UserInfo` objects (`operator`, `participant.user`, `transferTo`, `instance.applicant`, and list rows' `applicant`/`assignee`), one uniform shape everywhere — list DTOs never carry bare id/name pairs.
- **Integration engine is a runtime anti-corruption layer** (`vef.IntegrationModule`, tables `itg_*` on the primary source, `vef.integration.auto_migrate`): **Contract** (standard operation with self-contained draft-2020-12 input/output JSON Schemas — remote `$ref` rejected at save) / **System** (base URL + declarative outbound/inbound auth + optional outbound envelope scripts + non-sensitive `params`) / **Adapter** (one script per system × contract, unique-keyed) / **Route**. Business code injects `integration.Invoker` (or `integration.Call[T]`) and targets via `WithSystem` **or** `WithRoute` — both at once is `ErrTargetAmbiguous`, neither resolves the empty route key (the default route row). Route matching: exact `(key, contract)` beats contract-wildcard (`contract_id = ''`); the table-backed `RouteResolver` is replaced via `fx.Decorate`. Definitions are **not versioned** — saves are live immediately; compiled programs, resolved schemas, and per-system httpx clients all cache by content hash, so edits invalidate implicitly with no cross-node protocol.
- **Integration scripts get system-scoped capabilities, never the generic ones**: the runtime carries the js.Engine baseline (the stdlib bundle included — XML/SOAP adapters build and parse envelopes with its `fxp`, no integration-side wiring) plus the always-on `codes` library (per-system code map translation — see the code-map bullet) plus — only for systems with a `baseUrl` — `http` (per-system `httpx.Client` — base URL locked, **relative paths only** (absolute and scheme-relative URLs rejected), credentials injected host-side so scripts never see them, script-supplied timeout may only shorten the system call timeout, redirect modes beyond follow unsupported), `errors` (`errors.upstream(msg)` marks a throw as the upstream's fault), and — only for systems with a `dataSource` — `sql` (the jssql lib bound to the system database; read-only through sqlguard by default — `sql.execute` throws unless the data source declares `mode: "read_write"`, the lane for third parties whose integration surface is a writable exchange database); a script reaching for an unconfigured capability gets a plain ReferenceError. A system may configure `baseUrl`, `dataSource`, or both; the database connection registers lazily into `datasource.Registry` under the reserved `itg:<system code>` name, keyed by definition content hash (an edit re-registers on the next invocation; deleting the system or removing/renaming its data source unregisters it, and a missed release self-heals on restart). `test_connection` probes every configured transport (`http` + `database` probes). Per-run bindings: `input` (already validated against the contract's input schema) and `system` (code/name/params). The script body is wrapped in `(function(){...})()` — top-level `return` produces the standard model (reported line numbers shift by one), and the return value is validated against the output schema before the caller sees it.
- **Integration code maps translate code-set values per system** (`itg_code_map`, unique `(system_id, code_set)`; the code-level canonical-data-model instance): each entry pairs one **canonical** primary with one **external** primary plus optional per-side aliases — lookups match primary ∪ aliases by normalized string form (`1` and `"1"` address the same entry; values keep their JSON scalar type end to end), translations always emit the opposite side's primary (**aliases match, never emit**; save-time validation index-builds the entries and rejects per-side collisions, non-scalar values, and incoherent fallback config). Adapter scripts in **both directions** call `codes.toExternal('gender', v)` / `codes.toCanonical(...)` / `codes.entries(...)`; null/undefined pass through untranslated. An unmapped value resolves per the map's `on_unmapped` (`reject` fail-closed default / `passthrough` / `fallback` with per-side fallback values), overridable per call with `{ fallback: v }` / `{ passthrough: true }` / `{ reject: true }` (options are validated eagerly — a typo fails even on mapped values). Missing/disabled/unbuildable maps and rejected values classify as `config` (`ErrMissingCodeMap` / `ErrUnmappedValue` / `ErrInvalidCodeMap`, codes 2627-2629) — the fix is a code map edit, not a script change. Compiled lookup indexes cache by content hash (saves live on the next invocation; one run memoizes per code set). The canonical side's identifiers should agree with the host catalog: `mold.CodeSetResolver` / `mold.CodeSetLoader` (the renamed dictionary vocabulary; tag prefix `translate=codes:<codeSet>`, event `vef.translate.code_set.changed`) is the host seam, and a registration that also implements `mold.CodeSetInspector` (inspector pattern; asserted from the **loader first** — the mold module wraps loaders in its cached resolver, which would hide the enumeration — then the resolver) lights up the React mapping editor's code-set/value pickers via `integration/code_set.list_code_sets` / `list_codes` — without it the editor degrades to free text. The React page (`IntegrationCodeMapPage`) mirrors the entry validation and the typed-literal input convention (bare `1`/`true` → JSON types, quoted `"1"` → string); keep the two sides in lockstep.
- **Outbound envelope scripts live on the System**: `System.OutboundEnvelope` (`request` / `response` script bodies; compile-checked at save, at least one required, only valid with a `baseUrl`) factors the wire structure most vendor APIs repeat on every endpoint — `{code, msg, data}` replies, signed request wrappers, SOAP envelopes — out of the adapters and around every `http.*` call an outbound adapter makes. The request script sees `request` (`{method, path, headers, query, body}`; fields it omits keep the adapter's values) and returns the wire request; the response script sees the fetch-shaped `response` and its return value **replaces** the Response object as the call's result — throw `errors.upstream(msg)` there to normalize vendor error codes once per system. Adapters opt out per call with `{ envelope: false }` (file downloads, health checks), which hands back the raw Response. The wire trace and invocation log record the wrapped request and raw response — the truth on the wire, not what the adapter saw. Envelope scripts run in the adapter's runtime (they see `system` and the stdlib; failures classify through the normal vocabulary and are catchable in the adapter), compile through the content-hash program caches, and a saved-broken envelope classifies as `config` (`ErrInvalidEnvelope`, code 2625). Inbound flows carry no envelope — the inbound adapter script already owns the reply shape.
- **One failure vocabulary, three consumers**: `integration.FailureKind` (`input_invalid` / `output_invalid` / `upstream` / `transport` / `timeout` / `canceled` — caller cancellation is distinguished from a run-timeout — / `script` / `config`, plus the inbound-only `auth` / `handler`) classifies every failed invocation identically in the invocation log (`itg_invocation_log`; `vef.integration.log.mode` = `off`/`errors`/`all`, default `errors`; captures are masked — `Authorization`-class headers always, plus `password`/`token`/`secret` and `vef.integration.log.mask_fields` JSON keys/query params, plus every resolved auth credential value scrubbed by value so a multi-pair `header`/`query` or `script` credential never leaks under a name the fixed mask set cannot know — and truncated to `capture_limit`), in the per-node stats (`sys/monitor.get_integration_stats`, keyed by system × contract × direction, consumed by monitor through the optional `integration.StatsInspector`, mirroring `event.StreamInspector`), and in the API errors (codes 2600-2699, `errors.Is` works via code equality). Log rows are kept forever unless `vef.integration.log.retention` is set (deletion of the evidence trail is strictly opt-in); the hourly prune sweep is idempotent by cutoff, so replicas need no lock.
- **Integration response caching is call-site opt-in only**: `WithCache(ttl)` per invocation; adapters/systems carry no cache config, and a cache hit bypasses stats and the invocation log (it represents no upstream interaction). Timeout resolution for a run: `WithTimeout` option > `Adapter.TimeoutMs` > `vef.integration.run_timeout` (default 30s); `System.TimeoutMs` is the per-HTTP-call bound, a different axis.
- **Integration secrets**: an `OutboundAuthScheme` / `InboundAuthScheme` declares its `SensitiveParams`; their values are encrypted at rest with `vef.integration.secret_key` (base64; unset ⇒ plaintext storage + boot warning, but previously-encrypted values then fail closed on load) using the cipher selected by `vef.integration.secret_algorithm` — `aes` (AES-GCM default, 16/24/32-byte key) or `sm4` (SM4-GCM 国密, 16-byte key; both `cryptox` ciphers default to GCM mode, CBC stays an interop option) — and stored with an `enc:` marker. Stored values carry no algorithm tag: they decrypt with the configured cipher, and a value sealed under a different algorithm or key fails GCM authentication (fail closed), so switching algorithms requires re-entering stored secrets. The same treatment covers the `dataSource.password`. Management reads mask them as `integration.MaskedSecret` (`"******"`); an update submitting the mask keeps the stored value (mask-without-prior is rejected). Outbound built-ins mirror the inbound vocabulary: `none`/`http_basic`/`bearer`/`header`/`query`/`signature`/`script` — `header` and `query` are **multi-pair** (the params map itself is the name → value credential set, every value encrypted via the SensitiveAll wildcard), `signature` sends the framework's HMAC convention (params `appId` + hex `secret`; the sending counterpart of the inbound signature scheme, so two framework deployments authenticate each other with configuration only), and `script` (signing body in `OutboundAuthConfig.Script`, compile-checked at save, zero-IO runtime per request seeing `request` + decrypted `params`, returns the credential headers to add — the fallback for vendor-specific signing: field selection, sort order, secret concatenation are all script logic). Both request-time schemes ride `httpx.RequestHook`; an auth-hook failure classifies as `config` (`ErrInvalidAuthParams`), never transport. `OutboundAuthScheme.Apply` receives the full decrypted `*OutboundAuthConfig`; `vef.ProvideIntegrationOutboundAuthScheme` overrides by name or adds new ones (same override-by-name semantics as JS libs). `integration/ops.dry_run` executes unsaved script content with the full masked wire trace — but its upstream calls are REAL; `test_connection` probes a saved system and reports transport failure as data, not error; `diagnose_routes` is the on-demand routing report (dangling adapters, disabled targets, wildcard gaps, uncovered contracts — `integration.RouteFindingKind` is a typed vocabulary the React side renders by kind, keep them in lockstep). Routing deliberately validates loosely at save (an adapter may be created after its route) — the diagnosis endpoint is the safety net. The `SensitiveAll` (`"*"`) wildcard in `SensitiveParams` marks every parameter sensitive (used by the `script` schemes and the multi-pair `header`/`query` schemes, whose parameter names are user-defined); a nil scheme masks everything, fail closed.
- **Integration inbound is the mirror flow**: adapters carry a `direction` (`outbound` default / `inbound`; unique key system × contract × direction — the two flows never see each other's bindings) and inbound scripts translate requests the external system initiated into contract dispatches. The protocol-blind pipeline is `exec.Receiver` (shares the Invoker's caches/stats/log substrate); the HTTP gateway is an `app.Middleware` registering the real route `POST /integration/inbound/<systemCode>/<contractCode>` (order 400 — MCP precedent) with per-(system, client IP) sliding-window rate limiting (`vef.integration.inbound.rate_limit`, default 120/min, per node). Script bindings: `request` (protocol/method/path/**lowercased** headers/query/body/clientAddr), `system`, and `dispatch(input)` — validates the contract input schema, runs the registered business handler, validates the output schema, returns the output; the script's return value is the external-facing reply (HTTP: a map carrying the **explicit `$response` marker** — `{ $response: { status, headers, body } }` — takes raw control of the reply; every other value, including maps that happen to carry status/body fields, renders verbatim as 200 JSON; envelope string bodies pass verbatim as text/plain unless the envelope sets its own Content-Type). Handlers register via `vef.ProvideIntegrationInboundHandler` (`integration.NewInboundHandler[I, O](contract, fn)`), exactly one per contract code (duplicates fail at boot), and must be idempotent — external systems deliver at-least-once. Inbound runtimes get **no http/sql capability** (the `codes` library is available — translating the caller's codes is the inbound script's core job): a "notification + pull" flow belongs in the handler, which can invoke an outbound contract. A dispatch failure stays classified (`input_invalid` / `handler` / `output_invalid`) even when the script catches it to shape a partial-success reply — a completed script owns the reply, the log records the truth. Pre-script failures render caller-actionable statuses (401 for failed verification **and** for unknown/disabled systems, so system codes cannot be enumerated; 404 only for missing/disabled contracts/adapters behind a verified caller; 400 input, 429 rate limit, 500 rest) because external callers act on status codes, not the result envelope. Verification rejections are counted in stats under the system with an **empty contract** (the contract code is unvalidated caller input at rejection time) and never touch the invocation log.
- **Inbound auth is fail-closed and three-tiered**: a system without `inboundAuth` refuses inbound delivery entirely; the `none` scheme opens it deliberately. Built-in `InboundAuthScheme`s mirror the outbound vocabulary (only `ip` is inbound-only — a source address is verifiable only on receive): `ip` (params.whitelist, comma-separated IP/CIDR), `http_basic`, `bearer` (params.token — verifies what the outbound bearer sends), `header` and `query` (**multi-pair**: each params entry is one name → expected-value pair, the request must match every pair, constant-time; an empty pair set is a config fault, never an open door), `signature` (reuses `security.Signature` — HMAC over system code + method + path with `x-timestamp`/`x-nonce`/`x-signature` headers, hex params.secret, replay-protected), and `script` (verification body in `InboundAuthConfig.Script`, compile-checked at save; runs in a zero-IO runtime — engine baseline plus `request` and decrypted `params` only, so a script can read secrets but has no channel to leak them; truthy return grants, script errors stay server-side). Tier order: built-ins → DI-registered Go schemes (`vef.ProvideIntegrationInboundAuthScheme`, override-by-name) → per-system script (hot fix-forward fallback). Every verification failure surfaces as the uniform `ErrInboundAuthFailed` (401); rejections are counted in stats (`auth` kind; missing scheme/params classify as `config`) but deliberately **not** written to the invocation log — unauthenticated traffic must not grow the durable evidence trail. `integration/ops.dry_run_inbound` runs an (unsaved) inbound script against a synthetic request with the business handler stubbed by a caller-supplied sample output — verification bypassed, no business code, nothing recorded, both contract schemas enforced for real.
- **Durable cron scheduling is config-gated and a separate lane from gocron**: the in-memory `cron.Scheduler` (gocron) remains the lane for process-local infra ticks (every node runs them; guard cross-replica work yourself). Business jobs that need persistence, cluster-wide single fire, misfire policies, a run journal, and crash recovery use the **durable schedule store**: register named handlers with `vef.ProvideCronJobHandler` (`cron.NewJobHandler` / `cron.NewTypedJobHandler[P]`, one handler per job name, duplicates fail at boot; `cron.WithDefaultSchedule` seeds an insert-if-absent schedule at start-up), manage schedules via `cron.ScheduleManager` or the `sys/cron/schedule` + `sys/cron/run` resources, and enable with `vef.cron.store.enabled=true` (+ `auto_migrate` for fresh `crn_schedule` / `crn_fire_request` / `crn_run` DDL on the primary source only). Migration never alters or repairs an existing schema: missing column type/nullability/width or index capabilities, and retired timeline columns, fail boot and require recreating the cron tables. Coordination is **database-native claim-advance** (`FOR UPDATE SKIP LOCKED` + advancing `next_fire_at_unix_ms` in the claim transaction) — no Redis, no `lock.Locker`; nodes only claim jobs whose handler is registered locally, so rolling handler deploys are safe. Regular trigger delivery is at-most-once per occurrence. `Recover` queues one durable request per run that did not complete — abandoned (node stopped heartbeating) or canceled by graceful shutdown — making those deliveries at-least-once (idempotent handlers required); recovery requests survive pause/resume and wait, rather than becoming `skipped`, while `concurrency_policy=forbid` sees an active run. Policies: `misfire_policy` `fire_now`/`skip` (also applied by `Resume` to the paused regular-cursor gap), `concurrency_policy` `forbid`/`allow`; a regular claim consumes a whole misfire gap and journals it as ONE `missed` row (`missed_count`). `Create` and any `Update` that recomputes the cursor both refuse an enabled schedule whose trigger yields no occurrence, so a schedule can never be silently edited into "enabled but can never fire"; an edit that leaves the timing untouched still reaches an already-spent schedule, so renaming or re-pointing one stays possible. Every `TriggerNow` call inserts an independent durable manual request without moving the regular cursor, so an overdue occurrence is neither overwritten nor conflated with the manual fire; interval triggers remain fixed-rate anchored to `starts_at_unix_ms` or the persisted creation anchor. Cron triggers are a strict kind-tagged union, and an omitted timezone canonicalizes to `UTC` so every node advances the same calendar. Run events `vef.cron.run.failed` / `vef.cron.run.abandoned` are best-effort notifications — the journal is the truth, and a run reports whichever terminal state actually reached it, exactly once: a handler finishing after recovery already took its run over has its outcome discarded and stays silent, so subscribers never see two terminal events for one run ID. Assumes NTP-synced nodes. The cron scheduling timeline uses Unix-millisecond fields exclusively in its schema, persisted models, events, previews, filters, and management mutations, so repeated wall times across a DST fold stay distinct; idiomatic Go contracts such as `ScheduleSpec` and `Execution` carry exact `time.Time` instants. Framework-wide audit fields remain metadata and never drive scheduling.
- **Server push is a best-effort downstream channel** (`push.Notifier` via DI; WebSocket endpoint gated by `vef.push.enabled`, default off): the Notifier is always injectable — while disabled or with no matching recipients a push is silently dropped, so reliable notification is business storage + client pull, with push as the real-time hint. Handshake auth reuses the configured token mechanism through `security.AuthManager` (bearer header or the `__accessToken` query parameter — a browser cannot set WS headers); origins check against `vef.push.allowed_origins` (empty = allow all; token auth already keeps cross-site pages out). Targets are data (`push.ToUsers` / `ToRoles` / `Broadcast`, unioned and deduplicated; roles snapshot at handshake; an empty users/roles selector is rejected with `push.ErrNoTarget` — silent zero-recipient delivery is always a caller bug). Close codes are a client contract: `4401` (session invalid) and `4429` (per-user cap) are terminal — no auto-reconnect — while transport failures reconnect with backoff. Under `opaque_token` a periodic sweep (`vef.push.session_recheck_interval`, default 60s) revalidates connections via `SessionStore.Lookup` — deliberately not the authenticator, whose sliding renewal would turn an idle open tab into a session keepalive — and kicks dead sessions with 4401; under `jwt_token` the handshake is the only auth point (the token is unrevocable by design; exp does not drop live sockets). **Multi-node**: with the Redis client available, pushes and kicks relay through Redis Pub/Sub (`vef:push:relay:<vef.redis.database>:<vef.app.name>`, origin-deduped; the database+app-name namespace is mandatory isolation — Pub/Sub channels are server-global and NOT scoped by the Redis database number, so co-tenant apps or environments sharing one Redis would otherwise cross-deliver, and an enabled relay fails fast at boot when `vef.app.name` is empty; deliberately not Streams — every node needs every ephemeral frame, and consumer groups would leave the orphaned-group garbage the framework already sweeps); local delivery never waits on Redis, and a publish failure degrades to node-local delivery. **Instant revocation kick**: the framework fires `security.SessionRevocationNotifier` on logout and evict-oldest (挤下线), and the push module's `SessionRevocationListener` closes the revoked session's connections everywhere at once — the opaque handshake captures the session ID via one extra `Lookup` for exactly this. App code revoking directly against the `SessionStore` should fire the injected notifier itself; a missed notification degrades to the sweep (≤ recheck interval), never to a stale grant. Custom listeners (audit, admin dashboards) register via `vef.ProvideSessionRevocationListener`. A client too slow to drain its `send_buffer` queue is dropped, never allowed to block the fan-out.
- **The API manifest is exported by the application, and building the graph is enough**: `vef.ExportAPI(w, options...)` renders every registered operation as JSON — resource, action, auth strategy, permission token, audit flag, effective timeout and rate limit, and the request payload's full shape — and `vef.Run` delegates to it when `VEF_EXPORT_API` names a destination (`-` for stdout), so a host needs no second entry point. It reads the surface through `api.EngineInspector`, an optional interface (`Operations() []*Operation`, ordered by identifier) that `internal/api.engine` implements — an inspector rather than a method on `Engine`, matching `event.StreamInspector` and its siblings, so adding introspection breaks no host that implements `Engine` itself. **Nothing starts and nothing connects**: resources register during `provideEngine`'s construction, the data source opens lazily, and `mountOperation` — which is what invokes a crud handler's factory — only runs after `Mount`. That is why the export is safe in a container build or CI. The manifest is sorted and carries no timestamp because it is meant to be committed: its diff is the diff of your API contract, and `vef-cli export-api --check` is the CI gate that keeps the two in step. Handlers reach the exporter unadapted, so the payload is found through the resolver's `handler.Func` wrapper (which knows whether the function is a factory) and identified by its embedded `api.P` — never by guessing at the parameter list. **Whether a struct is expanded or named is decided by `json.Marshaler`/`encoding.TextMarshaler`, not by its package path**: a type that marshals itself does not reach the wire as an object at all, and `timex.DateTime` — which serializes to a string — expanded into an entry with no fields, because everything `time.Time` carries is unexported. Deciding by path instead gets it wrong twice, missing first-party marshaling types and, via the usual "no dot in the first path segment" test for the standard library, swallowing every package of a module whose `go.mod` name has no dot. **The type walk guards cycles on both paths.** The `types` map terminates a named field that reaches back to its own type; anonymous embedding is flattened rather than recorded, so it needs its own visited set, and a struct embedding a pointer to itself is legal Go that would otherwise exhaust the stack — a fatal runtime error that would take down whatever process the export ran in. The type being described belongs in that set too, or it flattens one copy of itself into itself and reports every field twice. **Result types are deliberately absent**: crud handlers return only `error` and write the response through `ctx`, so `TModel` is nowhere in the signature; adding them needs an appended `OperationSpec` field that crud fills from `reflect.TypeFor[TModel]()`, which is the planned next step, not an oversight. The same gap swallows `delete`/`delete_many`, whose handler takes the untyped `api.Params` bag rather than a typed struct, so they report no payload where they really take the model's primary keys — one declaration on `OperationSpec` closes both cases, which is why neither is patched over with a special signal now. Two things had to be fixed for the export to be honest, and both are now invariants: `Operation.RateLimit` **merges** the engine default field by field instead of choosing (a spec that sets only `Max` — as the login endpoint does — used to report `Period: 0`, which reads as unbounded while the request path silently applied the default), and the env-driven path raises the log threshold, because module loggers write to **stdout** and would otherwise land in the middle of a manifest bound for `-`.
- **`internal/schema` opens its Atlas inspector on first use, not in its constructor, and remembers only success**: `postgres.Open(db)` and friends query the server, so building it eagerly made the whole fx graph unresolvable without a reachable database — the same reason `internal/datasource` opens without blocking and pings from a start hook. `NewService` still validates the dialect eagerly (a pure check, so a misconfigured kind fails at boot as before); only the connection is deferred. A failed open is deliberately **not** cached — opening queries the server for its version, so it can fail for reasons that pass, and memoizing that failure would leave schema inspection broken for the whole life of the process, recoverable only by a restart. That would be strictly worse than the eager construction it replaced, where a failure at least took the boot down and let the supervisor retry. `schema.Column` also carries **`MaxLength`** separately from `Type`, because `Type` is the dialect's own spelling and does not consistently include the bound: PostgreSQL reports `character varying` with the length held elsewhere, MySQL reports `varchar(128)`. Read the bound from `MaxLength`, never by parsing `Type`.
- **A contract an application implements must live in a public package**: fx matches a group by exact type, and a provider whose type does not match is **dropped without an error** — `fx.New` returns nil, boot succeeds, the extension simply never runs. Structural identity does not help: two named interfaces with the same method set are different `reflect.Type`s, so an application cannot rescue itself by re-declaring the interface. That is why the `Middleware` contract lives in the public `app` package with `internal/app` holding `type Middleware = app.Middleware` — an alias, so the framework's own references stay unqualified while the two types remain one. Before that split, `vef.ProvideMiddleware` was unusable by every real host: applications are a different Go module and cannot import `internal/app`, so nothing they provided could ever match the group, and the failure looked like a route that silently refused to register. `TestProvideMiddlewareReachesTheRouter` (`di_test.go`) is the guard and deliberately declares its collector as `[]iapp.Middleware` — the framework's own consumer type — while registering through the public one; `TestProvideAuthenticatorReachesTheAuthManager` pins the same property for `security.Authenticator`. Apply the rule to every new extension point: put the contract where a host can name it, then add the `vef.Provide*` helper beside the others.
- **No `logx.Logger` in the FX graph**: module loggers are package-level `internal/logx.Named("<module>")` by convention. A constructor wired into DI must not declare `logx.Logger` as a dependency — fx resolves lazily, so the missing provider only explodes when the first consumer appears (this bit the js engine wiring; its module now closes over the package logger).
- **No `context.Context` in the FX graph either**: fx provides exactly three types of its own — `Lifecycle`, `Shutdowner`, `DotGraph` — so a constructor or `fx.Invoke` target declaring `context.Context` as a parameter aborts the entire application with `missing type: context.Context`. Start-up work that needs a context registers a lifecycle hook instead — `lc.Append(fx.StartHook(func(ctx context.Context) error { ... }))` — which receives the context fx manages for start-up; every module's schema migration follows that shape. A config gate must sit **inside** the hook whenever anything runs unconditionally: approval verifies its schema on every boot, so copying storage's `if !cfg.AutoMigrate { return }` early return would silently skip the check. `TestBootOptionsGraphResolves` (`bootstrap_test.go`) runs `fx.ValidateApp` over the core sequence plus each optional module and is the standing guard; a test harness must never repair the graph by supplying a `context.Context` of its own, which is exactly what kept both optional modules unbootable while their own suites passed.
- **The cron scheduler starts from the trailing slot, and start-hook order is otherwise unspecified**: fx runs start hooks in append order, and a hook appended from a constructor lands wherever that constructor first resolves — which for the shared gocron scheduler was the first job registration, far ahead of the hooks that migrate the tables those jobs read. So `internal/cron.Module` only builds the scheduler and `cron.StartScheduler` runs it, from the trailing slot `bootmodules.Assemble` reserves after the host's options. That is what makes the start-hook migration pattern sound: no job — not even one registered with `cron.WithStartImmediately`, as the approval business-projection worker is — ticks against a schema that does not exist yet. **The trailing slot must stay a bare `fx.Invoke`, never an `fx.Module`**: fx runs every child-module invoke before any root-level one (`fx/module.go`, `invokeAll`), so a module there is still overtaken by a host option written as a plain `fx.Invoke` — which is how the first version of this fix was wrong. Ordering last also means stopping early, which is what shutdown wants: jobs stop before the event bus and the data sources they use, while `startApp` is appended after and so drains HTTP first, leaving no handler holding a dead scheduler. **The one class this does not cover** is constructors nothing resolves until `startApp` builds `app.App` — host API resources (`vef.ProvideAPIResource`), middleware (`vef.ProvideMiddleware`), and `fx.Decorate` over either; a start hook appended from one of those runs *after* the scheduler. Moving the invoke past `startApp` would cover them but flip shutdown (scheduler dead before HTTP drains), so the placement stands and provisioning belongs in a module, never in an API resource's constructor. `TestSchedulerStartsAfterModuleAndHostStartHooks` (`bootstrap_test.go`) is the guard and pins both the module and the bare-invoke case. **Do not rely on start-hook order between two modules for anything else** — a module whose worker must not run before its own provisioning should do both in one hook, the way the durable cron store does (`internal/cron/store.registerLifecycle`: migrate → verify → seed → `engine.Start()`).

## CLI Tools

`cmd/vef-cli` is split into two command families, and **the split is a contract with the developer, not cosmetics**: `new` writes a file once and hands it over — no generated-file header, never regenerated, safe to edit — while `generate-*` and `export-api` own their output forever and overwrite it on every run. The test for which family a new command belongs to is one question: *will anyone want to edit this?* Yes ⇒ `new`; no ⇒ a derived artifact with `// Code generated ... DO NOT EDIT.`. Blurring the line is how a generator becomes a command nobody dares to run.

- **`new project <name>`** — the standard layout (`cmd/server`, `configs/application.toml`, `internal/<module>/{model,payload,resource,service}`, `internal/vef` for build metadata, `vef.yml`, `.golangci.yml`, `Taskfile.yml`). It pins the framework to the CLI's own `version.VEFVersion` (the tool generates against the API it was built from, which cannot go stale) and runs `generate-build-info` before finishing, because `internal/vef/module.go` references `BuildInfo` and that file is generated rather than committed — without it a fresh project greets you with an undefined identifier. Deliberately excluded: Dockerfile, git hooks, CI. Those are deployment and team decisions; the framework only generates what the framework decides.
- **`new resource --table <t> --module <m>`** — model + payload + resource from a live table, **plus both registrations** (the model registry's `var` block and the module's fx option list). The registrations are half the value: forgetting one produces an application that compiles and answers 404. Inference: column comment → `label`, nullable → pointer + `omitempty` + `validate:"omitempty"`, declared bound → `max=N`, and a table carrying the framework's audit columns embeds the matching `orm` mixin instead of re-declaring them (widest match wins). **Three properties here are load-bearing and each has a test naming the failure it prevents.** (1) *The mixin match checks column types, not just names.* `orm.Model` declares `ID string` and the ORM writes a generated XID into any zero-valued string primary key on insert, so matching a `BIGINT` identity column on its name alone would push a 20-character string into a numeric column on every create. A table whose audit columns are typed differently matches nothing and has them generated as ordinary fields, which is honest and still correct. (2) *Every key column the mixin does not supply carries `bun:",pk"`.* `FullTrackedModel` and `CreationTrackedModel` exist precisely for composite keys and declare no `ID`, so without this the model reaches bun with no primary key and every `Update`/`Delete` fails at runtime with `ErrModelNoPrimaryKey` — and `HasIDField`, not "a mixin matched", is what decides whether the payload carries an `id`. (3) *A field states its column explicitly whenever the name does not derive back.* bun re-derives the column from the field name and that derivation is not the inverse of `naming.PascalCase` — `api_v1` becomes `APIV1`, which derives back to `apiv1` — so the generator verifies the round trip per field with `naming.SnakeCase` rather than trying to make the heuristic reversible for every input. That check is what makes names nobody has thought of yet safe, including a column starting with a digit, which `PascalCase` escapes into a legal identifier. `find_tree` is refused rather than rendered, since `crud.NewFindTree` takes a tree-building function no generator can supply. Search criteria default to every scalar column (string → `contains`, else `eq`) because deleting what a screen does not need is a smaller edit than discovering what exists; `--search col:op` or `--search none` overrides. A module that does not exist yet is created, skeleton and all — **and wired into `cmd/server/main.go`'s `vef.Run` call**, because a new module that registers nothing is the same 404 one level up. That last step is best-effort: the entry point's path and shape are a convention, not a contract, so a project that wires itself differently gets a `TODO` line instead of a failed command.
- **`new service --name <n> --module <m> [--deps field:Type]`** — the convention-shaped skeleton (struct of injected deps only, methods take `(ctx, db orm.DB, …)`), registered with its module. Framework dependency types resolve their own imports.
- **`export-api`** — see the API manifest gotcha below. Two rules make it composable, and both were learned the hard way: **progress goes to stderr, never stdout** (`cliout.PrintLabeledLine` takes its destination as a parameter for exactly this — hardcoded to stdout, `-o -` put a human-readable line in front of the manifest and every pipe into `jq` failed, the same class of bug as the framework logger writing to stdout during export), and **`--check` with `-o -` is refused, not ignored** — a CI job written that way compared nothing and exited 0 on every drift, which is the one failure a gate must not have.
- Conventions come from **`vef.yml`** at the project root (`project.Config`): `module_root`, and under `resource` the `name` / `permission` templates (placeholders `{module}` — the full, possibly nested path —, `{domain}` — its first segment, which is what permission tokens scope to —, `{entity}`, `{action}`), `ops`, `audit`, `audit_user_model`. Every key has a default, so the file is optional; `new project` writes one so the conventions are visible rather than implied. It is read with viper, the same dependency that already reads `application.toml`. **`module_root` and `--module` are import-path elements, not just directories, and are validated as such at the point they are parsed**: `filepath.Join` swallows a dot segment, so `module_root: "."` used to build the right directories and the import path `acme/./md/model`, which the compiler rejects — it now normalizes to the empty string (modules at the project root) and `ImportPath` drops empty segments, while a root escaping the module (`../shared`) is refused outright. `--module` is checked one step further, per segment against `token.IsIdentifier`, because each segment is a directory holding Go packages and the last is a package name; without that a stray `--module ""` or `hr-emp` surfaced only as a syntax error inside a file the generator itself had just rendered, which reads as a bug in the tool. Neither value reaches a template unvalidated. Templates likewise never declare their own imports — `render` inserts every one through `gopatch` so grouping has a single implementation — so a template carrying an empty `import ()` placeholder shipped it verbatim whenever nothing was inserted (a `new service` with no `--deps`), since gofmt keeps an empty import declaration.
- **Shared machinery lives in `cmd/vef-cli/cmd/internal/`, one owner per concern**: `naming` (table ↔ entity ↔ alias ↔ file ↔ permission — the *only* place these conversions happen, or four commands drift), `gopatch` (AST-located, text-spliced edits to existing files plus gci-correct import insertion), `project` (go.mod discovery, `vef.yml`, and the `schema.Service` inspector). `scaffold.Plan` is the shared write engine: every command plans all its effects first, so `--dry-run` shows the whole thing and a mid-planning failure leaves nothing half-written.
- **`gopatch` never reports a job done that it did not do.** A path already imported under a different name — an alias, a blank, a dot import — is an `ErrImportNameConflict`, not a satisfied import: the generated selector would resolve to nothing, and since the file still *parses*, `Format` would not catch it and the plan would write uncompilable code. Insertions are equally careful about text they did not write: an entry appended beside a comment sharing the closing parenthesis's line goes onto its own line rather than copying that comment, and a new import sorts above a documented one's comment rather than between the comment and the import it describes. Each of these produces valid Go when it goes wrong, so nothing downstream catches it — which is why they are tested rather than trusted.
- **A `Plan` patch closure must report a change when *any* of its steps made one.** `AddPatchOrCreate` discards the buffer of a patch that reports none — that is what makes a re-run a clean "already registered" instead of a rewritten file — so a closure returning only its last step's flag silently drops the earlier edits. `planModuleRegistration` runs three (two imports, then the fx option) and returned only the third, so a module already carrying the option but missing an import was recorded as unchanged and left uncompilable. `TestModuleRegistrationCountsEveryStep` is the guard.
- **`gopatch` splices text at AST-located positions instead of re-printing the parsed file.** Re-printing would rewrite parts the generator never touched, and these are files the developer owns — a one-line addition must read as a one-line diff. Every patch is idempotent (an argument or declaration already present is a no-op, compared with whitespace normalized), which is what makes re-running a generator over existing code safe.
- Keep Cobra wiring in `command.go`; move reusable generation logic into `generator.go` or `templates.go` only when it improves clarity.
- Command packages use idiomatic single-word lowercase names (for example `buildinfo`, `modelschema`, `scaffold`, `exportapi`), and the exported constructor is `Command() *cobra.Command`. The package name need not match the command word — `new` is a Go keyword, so the `new` command lives in `scaffold`.
- Each `RunE` sets `cmd.SilenceUsage = true` on entry. Reaching `RunE` means the flags were valid, so anything that fails afterwards is a failure rather than a misuse and its reason must not be buried under usage text. Do **not** do this from a `PersistentPreRun` on the root: cobra runs that hook *before* `ValidateRequiredFlags`, so it would also suppress usage for the missing-flag case, which is exactly when usage helps.

`cmd/vef-lint`: the repository's own `go/analysis` analyzers, for conventions no off-the-shelf linter can express. It is a `multichecker`, so each rule gets an enable flag of its own (`-unusedrecv`, `-unusedparam`) while the shared `-fix` applies every suggested fix in place and `-diff` previews them instead. Test files are analyzed by default (`-test`).

- Rules live one per file in `internal/lint` (`unusedrecv.go`, `unusedparam.go`) and join `Analyzers()` in `lint.go` — that registration is the only wiring a new rule needs.
- Shared inspection helpers are in `funcdecl.go`: `funcDecls` (yields `(file, decl)` pairs; skips generated files, bodiless declarations, and function literals), `isReferenced` (resolves through `TypesInfo`, so a shadowed name is not mistaken for a used one), and `holdsComment` (both rules fix by replacing the span from an identifier to its type, so a comment written inside that span — `func f(a, // why\n b int)`, `func (r /* the repo */ *T) M()` — would be deleted by the fix; the diagnostic still fires, the `SuggestedFix` is withheld and says so).
- Every rule is tested with `analysistest.RunWithSuggestedFixes` against `testdata/src/<analyzer>/a.go` plus its `.golden`, which pins the diagnostics **and** the fixes. A fix that rewrites a signature must be tested against grouped parameter names: `_, _ string` is two parameters, so deleting names without repeating the type silently changes the function's arity — and the result usually still compiles.
